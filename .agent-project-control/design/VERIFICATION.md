# 1. 共享设计基线验证合同

设计规则的验证必须进入当前 Turn 的 Checklist 与 TEST，而不是维护第二套独立执行账本。D 规则负责说明设计义务和建议验证方法，APCF R03/R06/R07 负责当前验收事实、证据和结论边界。

## 1.1. 当前 APCF 映射

- 当前任务先把用户要求和适用 D 规则转化为当前 `CHECKLIST.md` 的 CL 条目；D 编号可以作为依据引用，但不能替代用户要求。
- 一个 CL 可以由多个 TEST 覆盖不同失效面；一个 TEST 只有在同一份证据直接证明多个 CL 时才引用多个 CL。
- `TEST.md` 使用 APCF v0.2.3 的一行式当前验收表单，只保存当前 Turn 当前候选的有效验收结果，不继承 Attempt 历史。
- 中途调试失败和过程日志进入当前 TR 的 `evidence/` 或 `runtime/`；具有长期复发价值的设计失败提升为 REG。后续 Turn 需要回归时重新生成当前 TEST，不复制旧 TEST。
- 设计验收优先使用实际界面、关键状态、输入方式、响应视口和真实数据变化；截图、技术测试、用户认可、部署状态不能互相替代。
- Profile 参数只在项目已采用对应 Profile 或有真实项目依据时成为验收对象；不能把样板默认值自动升级成所有项目的硬门槛。

## 1.2. 原则、实现与验证边界映射

下表记录源样板的方法映射，源码名称和旧实验仅用于解释迁移背景；例如 latency_probe.py 未随参考包分发，本次没有运行该实验，不能把这些描述当作当前项目已验证结果

| 关注面 | 依据／方法 | 当前实现或规则位置 | 边界 |
|---|---|---|---|
| 活动栏与搜索内间距 | 接近性、可辨命中区；S14/S17 | D03/D04/D13；geometry角色参数 | 64/44/40等是样板候选值 |
| 搜索范围与清除 | 全局与局部入口；S13/S15 | D01/D10；clearSearch、filterPalette | 不包含网络全文检索或私密搜索历史 |
| 聚焦、选中、执行 | 焦点与激活区分；S13/S16 | D01/D11；活动栏、树、命令结果 | 本轮未测真实屏幕阅读器 |

## 1.3. 使用方式

- **改设计**：从当前用户要求定位相关 D 编号和义务子项，读取触发、必须、验证与例外，再把真正适用的结果要求写入当前 Checklist。
- **改实现**：使用目标项目原生构建、测试和真实入口验证；证据绑定当前候选、输入、环境与实际观察。局部技术信号不能升级成用户已认可或生产已部署。
- **采用 Profile**：先在项目 `DESIGN.md` 明确记录采用状态与差异，再使用 Profile 参数或参考实现；不得通过存在一个 Profile 就推导项目已采用。
- **规则演进**：共享 D 规则变化只修改 `design/RULES.md`，Profile 参数变化只修改对应 Profile；项目差异只修改项目 `DESIGN.md`。三层不能平行维护同一事实。
