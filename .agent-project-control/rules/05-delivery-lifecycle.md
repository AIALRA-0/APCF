# 5. 部署、版本与生命周期

本文件是 `05-delivery-lifecycle.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 5.1. R15 已有正常部署路径且部署属于当前授权范围的可部署项目，默认采用“修改 → 必要前置检查 → 部署 → 真实入口验收 → 继续修改”的真实环境闭环；除非用户明确要求本地预览或存在真实不可逆风险，不得长期停留在本地

### 5.1.1. 原则

- 当任务修改的是已有可部署、可访问的应用、网站、服务或产品时，因本地环境只能证明本地候选，而用户真正使用和评价的是实际上线结果，如果智能体反复在本地修改、测试、截图和优化却不更新真实用户入口，就会形成“本地一直通过、用户始终看不到”的伪迭代，所以在已有正常部署路径且部署属于当前授权范围时，默认应将通过必要最低限度前置检查的修改**直接部署到实际用户使用的环境，并以真实入口继续验收和迭代**；只有用户明确要求本地预览或真实上线存在不可忽略的外部风险时，才停留在本地；

### 5.1.2. 触发

- 修改已有网站、Web App、服务、应用或其他存在真实用户入口的项目时；
- 当前项目已经存在可用部署流程时；
- 本轮修改已经达到能够运行或进入真实环境验证的状态时；
-智能体准备连续进行多轮本地预览、本地截图或本地模拟测试时；
- 本地结果与用户实际访问结果可能存在环境差异时；
- 用户正在等待查看修改后的实际效果时；

### 5.1.3. 必须

- 已有正常部署路径且部署在当前授权范围内时，默认工作循环必须是：

  **修改 → 必要前置检查 → 部署 → 真实入口验收 → 继续修改**

  而不是：

  **修改 → 本地测试 → 本地测试 → 本地截图 → 本地继续优化 → 长期不部署**

- 本地验证只承担**部署前能够快速发现明显错误的必要检查**，不得被当成最终交付环境；
- 不得仅因为“还可以继续本地优化”“想再保险一点”“先把本地做完美”而无限推迟上线；
- 当用户没有明确要求本地预览时，不得把“本地预览确认后再上线”自行增加为用户必须参与的 门禁；
- 对 UI、交互、部署配置、网络、认证、持久化或环境相关功能，真实用户入口能够提供更直接证据时，必须尽早进入真实环境验证；
- 每轮修改达到可部署状态后，应通过版本管理保存当前可恢复状态，然后部署，而不是额外复制整个项目目录作为“安全备份”；
- 部署后必须按照第 6、7 条在实际入口检查当前修改真正相关的结果；部署成功本身不等于验收成功；
- 真实入口发现问题时，应继续按照：
  
  **定位 → 修改 → 必要检查 → 再部署 → 再验收**
  
  快速迭代，不得因为线上第一次发现问题就退回长期本地开发模式；
- 当前任务本身就是修复线上问题时，完成标准默认包含对应修复已经到达实际目标环境，而不是只存在于本地工作树；
- 如果部署失败但仍属于原授权范围，应按照第 4、8 条继续诊断、修复并重试，不得把第一次部署失败变成新的用户确认点；
- `CHECKLIST.md` 和 `TEST.md` 必须区分：
  - 本地候选通过；
  - 已部署；
  - 真实入口通过；
  
  不得用前两者替代最终真实效果；

### 5.1.4. 例外

- 用户明确要求“先只做本地版本”“不要上线”“先给我预览”时，遵守用户指定边界；
- 项目不存在任何可部署环境或智能体当前没有部署能力时，不得虚构部署；
- 当前修改涉及无法由 Git 直接恢复的外部不可逆副作用，例如：
  - 破坏性数据库迁移；
  - 删除生产数据；
  - 支付或真实资金动作；
  - 对外发送不可撤回内容；
  - 不可逆账号或基础设施操作；
  
  必须先处理这些真实风险；**Git 可以恢复代码，不代表能够恢复所有外部状态**；
- 项目已有明确的 staging、preview、canary 或发布规范时，真实部署按照该项目既有发布路径执行，不得为了本规则绕开正式约束；
- 法规、安全、平台或用户明确规定需要发布审批时，遵守该真实要求；

**错误示例（Bad Example）**：

- 用户要求修改网站 UI；
- Agent连续迭代 8 次：
  - 本地启动；
  - 本地截图；
  - 本地 Playwright；
  - 再修改；
- 用户打开实际网站仍然是旧版本；

**正确示例（Good Example）**：

- Agent完成第一版可运行修改；
- 执行必要的快速前置检查；
- 保存版本状态并部署；
- 从用户真实入口检查布局和交互；
- 发现问题后继续修改并重新部署；
- 用户始终能够看到最新有效迭代；

**错误示例（Bad Example）**：

- Agent说：
  - “本地已经全部测试通过，如果你确认我再上线；”
- 用户此前已经授权完成整个修改任务，也没有要求本地预览；

**正确示例（Good Example）**：

- 不新增“用户先确认本地效果”这个不存在的 门禁；
- 在已有部署授权和正常发布路径下直接进入部署；
- 在真实入口完成最终验证；

**错误示例（Bad Example）**：

- 线上 UI 有一个小问题；
- Agent因为担心回滚，先复制：
  - `project_backup_1`
  - `project_backup_2`
  - `project_final`
  - `project_final2`
- 随后一直本地修改，不敢部署；

**正确示例（Good Example）**：

- 代码由 Git 保存可恢复版本；
- 可部署候选完成必要检查后直接部署；
- 有问题使用版本历史进行代码回退或修复；
- 不用目录复制代替版本管理；

## 5.2. R16 代码和适用文本资产必须使用 `Git` 增量历史管理；不得用全量目录副本代替版本控制；`Git AI` 可在可用时承担人工智能归因；过时下载、测试输出、构建产物和临时残留必须按真实生命周期清理

### 5.2.1. 原则

- 当智能体持续迭代项目时，因每轮复制整个目录、保存多个 `backup / final / old / v2 / v3` 副本以及长期保留过时下载、测试输出和临时产物，会产生多个事实源、浪费空间并使下一轮无法判断哪个版本才是真实当前状态，所以代码和受版本控制管理的文本资产必须优先使用 **Git 的增量历史**保存变化，而不是通过全量复制制造备份；AI 产生的修改在工具可用时使用 **Git AI** 等归因机制记录来源，同时定期清理已经失效且可重新生成的临时残留，使工作区始终保持单一当前状态和可追溯历史；

### 5.2.2. 触发

- 开始或接管持续迭代的软件项目时；
- 修改已经受 Git 管理的代码、配置、文档或测试资产时；
-智能体准备为了“保险”复制整个项目或文件形成备份时；
- 出现 `backup / old / final / final2 / copy / v1 / v2` 等重复版本时；
- 完成一轮稳定修改、修复或部署时；
- 工作区积累旧下载、截图、日志、构建产物、临时测试数据或废弃输出时；
- AI智能体对代码进行持续修改且 Git AI 或等价归因机制可用时；

### 5.2.3. 必须

- 持续迭代项目必须优先使用 Git 作为代码和适用文本资产的版本历史；
- 已纳入 Git 的内容修改时，默认通过**增量 commit / diff**记录变化，不得为了保存旧状态复制整个项目；
- 每个达到有意义、可恢复状态的修改应形成清晰的版本边界，使后续能够判断：
  - 修改了什么；
  - 为什么修改；
  - 当前基线是什么；
  - 必要时从哪里恢复；
- 不得产生无必要的：
  - `project_backup/`
  - `project_backup_2/`
  - `file_old.*`
  - `file_final.*`
  - `file_final_v2.*`
  - 时间戳全量项目副本；
  - 其他与 Git 历史职责重复的长期备份；
- 需要比较旧版本时必须优先使用 Git diff、log、branch、tag、commit、worktree 或其他 Git 原生能力，而不是长期保存平行目录副本；
- 当 Git AI 可用并支持当前 智能体/环境时，应使用它作为 Git 之上的 AI 归因层，记录 AI 修改与 智能体、模型、Prompt / Session 之间的关联；不得把 Git AI 错当成 Git 本身或独立全量备份系统；
- Git AI 或其他归因工具不可用时，不得阻塞正常 Git 版本管理；版本历史的基本可靠性不能依赖归因附加层；
- 临时下载、安装包、抓取文件、截图、测试输出、构建缓存、日志、一次性诊断产物等必须区分：
  - 当前仍被使用；
  - 需要作为验收证据长期保留；
  - 可以重新生成；
  - 已经失效；
- 已确认失效、被替代且不再承担证据或恢复作用的临时产物必须定期清理，不得无限堆积；
- 自动测试可以重新生成的普通输出不得被当成永久历史档案保存；
- `TEST.md`、`CHECKLIST.md`、REG 条目或正式证据仍引用的文件，在引用有效期间不得因为“清理”直接删除；
- 清理旧残留前必须判断是否仍存在：
  - 当前引用；
  - 唯一证据价值；
  - 无法重新获取的数据；
  - 用户要求保留的历史价值；
- 对需要长期保存的大型二进制、数据集、模型、发布包或其他不适合普通 Git 的资产，应使用项目已有的适当存储机制，不得为了遵守本规则强行塞入 Git；
- 工作区必须尽量保持**一个明确当前版本 + 可追溯历史**，不得让多个平行副本同时声称自己是最新版；
- 版本管理的目标是支持频繁修改和可靠恢复，不得因为担心回滚而阻止正常迭代和部署；
- 模板源仓库和下游项目的历史职责必须区分：模板源仓库的旧部署轮次、旧导入材料和可重建验证产物如果已经由 Git 保存且不再被当前报告或长期规则引用，可以从当前工作树压缩掉；下游真实项目的历史不得因为模板维护而被自动删除
- 模板源仓库进行历史压缩时，至少必须保留根目录 `CURRENT.md`、其对应当前或最近一次 TR 的 `TURN.md`、该 TR 的 `CHECKLIST.md`、`TEST.md` 以及仍被当前报告引用的证据；更早历史由 Git 提供恢复，不再要求在当前文件树常驻
- 对外分发的干净模板和 `bootstrap.py` 创建的新项目不得携带模板源仓库自己的 IT/TR 历史、原始材料、运行缓存或部署证据；这些目录必须以空索引与空运行区开始，避免把框架开发历史误当成新项目上下文
- 为方便交接，智能体默认从根目录 `CURRENT.md`、项目知识文件与当前索引恢复当前状态；只有需要追溯时才按 ID 加载历史 TR、REG、ADR、RB 或 MAT，不得在每次接管时全量扫描全部历史

### 5.2.4. 例外

- 用户明确要求生成一个独立归档、交付包、快照或不可变备份时，可以创建对应副本；
- 数据库、外部服务状态、用户数据、Secrets、大型数据集和其他不适合 Git 管理的状态必须使用其适当备份或恢复机制；不得错误认为 Git 能保护所有系统状态；
- 发布产物因平台、审计或交付要求需要保留历史版本时，可以按真实要求保存；
- 调试过程中需要短期复制一个对象进行实验时可以临时存在，但任务结束后必须决定其归档、纳入版本管理或删除，不能默认永久残留；

**错误示例（Bad Example）**：

每次智能体修改项目都创建：

- `project_20261001_backup/`
- `project_20261002_backup/`
- `project_final/`
- `project_final2/`
- `project_really_final/`

几轮以后无人知道哪个才是当前版本；

**正确示例（Good Example）**：

- 项目保留一个工作树；
- 修改通过 Git diff 表示；
- 有意义的状态通过 commit 保存；
- 需要并行实验时使用 branch / worktree 等已有机制；
- 历史通过 Git 恢复，不制造全量副本；

**错误示例（Bad Example）**：

- Agent下载了 18 个旧安装包；
- 保存了 70 张已经失效的 UI 截图；
- 留下 12 份测试输出和 9 个旧 build；
- 所有内容都因为“以后也许有用”永久保存；

**正确示例（Good Example）**：

- 当前证据仍引用的产物继续保留；
- 可重新生成且已经失效的旧 build、下载和测试输出清理；
- 真正具有长期回归价值的案例进入项目原生测试资产，并在 `.agent-project-control/regressions/` 中建立或更新对应 REG；
- 工作区不承担无边界档案馆职责；

**错误示例（Bad Example）**：

- 安装 Git AI 后，Agent认为：
  - “有 Git AI，所以不用 Git commit 了；”

**正确示例（Good Example）**：

- Git 继续承担版本历史和恢复；
- Git AI 在其上记录 AI 代码归因和对应智能体/ Model / Prompt 信息；
- 两者职责不混淆；

**错误示例（Bad Example）**：

- Agent为了保证安全，每次修改一个文件之前都先复制：
  - `config.before-edit`
  - `config.backup`
  - `config.old`
- Git 仓库里因此长期存在大量冗余副本；

**正确示例（Good Example）**：

- 修改前确认当前 Git 状态；
- 修改形成正常 diff；
- 必要时提交形成恢复点；
- 使用 Git 历史恢复旧内容；
- 不再维护与版本控制重复的人工副本；
