# 6. 框架数据与长期合同

本文件是 `06-framework-contract.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 6.1. R19 框架管理的文件和目录必须显式声明 `public/private`；文本使用统一头部标识，目录使用统一目录标识，二进制对象使用伴随元数据文件；缺失或冲突必须由确定性检查发现

### 6.1.1. 原则

- 项目同时存在公开文件、私有材料、内部证据和可发布产物时，仅靠目录名或智能体记忆判断可见性容易把私有内容错误发布，所以框架管理对象必须具有机器可检查的 `public/private` 声明
- 可见性元数据只解决“这个对象是否允许进入公开面”，不能自动证明内容没有秘密、版权问题或其他发布风险

### 6.1.2. 触发

- 框架创建或接管新的文本文件、目录或二进制材料时
- 对象准备进入 Git 提交、公开仓库、Release、外部传输或其他发布面时
- 文件移动、复制、派生或改变用途，可能影响其公开边界时

### 6.1.3. 必须

- 框架管理的文本文件在第一处机器可读元数据声明 `visibility: public` 或 `visibility: private`
- 框架管理的目录使用统一目录元数据声明可见性
- 无法安全嵌入文本头的二进制对象使用伴随元数据文件，并保存足以核对对象身份的内容摘要
- 可见性不能只从文件名、目录名、扩展名或智能体猜测得出
- 缺失元数据、声明冲突、二进制摘要不匹配、私有对象进入公开发布面时，确定性检查必须失败并指出具体对象
- 原项目接入框架以前已有的源码与资源不得仅为了框架元数据被批量重写；框架通过边界映射或发布检查保护这些对象
- 发布前还必须遵守实际发布流程的敏感内容审核；`visibility: public` 不是“内容一定安全”的证明

### 6.1.4. 例外

- 原项目已有成熟且等价的可见性或敏感性元数据体系时，可以建立映射，不强制复制第二套标签
- 只存在于宿主临时内存、不会落盘或进入任何传输面的瞬时对象，不要求人为创建持久元数据

**错误示例（Bad Example）**：

- 因为文件位于 `docs/`，智能体默认它可以公开并直接提交，其中实际包含内部地址

**正确示例（Good Example）**：

- 文件具有明确可见性声明；发布检查同时核对声明与实际传输面，发现 `private` 对象时拒绝进入公开提交

**错误示例（Bad Example）**：

- 一个 PDF 被替换为新内容，但旧伴随元数据摘要仍然保留，检查器只看文件名不核对内容

**正确示例（Good Example）**：

- 二进制伴随元数据记录当前内容摘要；摘要不匹配时检查失败，要求重新分类或更新元数据

## 6.2. R21 用户资料统一进入 `materials/`；智能体临时下载、测试、运行输出、缓存、大文件和临时副本统一进入 `runtime/`；证据和长期最小复现资料只能通过明确提升离开临时运行区

### 6.2.1. 原则

- 用户原始材料、长期证据和智能体临时产物具有完全不同的价值与生命周期；如果全部散落在项目根、下载目录或临时文件夹中，后续无法安全清理，也无法判断哪些对象必须长期保留，所以必须分开管理
- `materials/` 是用户与来源资料区；`runtime/` 是智能体可控靶场；正式证据和长期最小复现分别进入拥有它们的 TR、PA 或 REG

### 6.2.2. 触发

- 用户提供 PDF、图片、文档、数据、音频、压缩包或其他资料时
- 智能体需要下载依赖、创建测试环境、生成临时日志、缓存、大文件或中间副本时
- 临时对象被证明具有长期价值，需要提升为正式产物、证据、材料派生物或回归复现时
- 准备清理项目中的临时对象时

### 6.2.3. 必须

- 用户原始资料进入独立 `MAT-*` 单元；原件放入 `original/`，不得原地修改
- 从用户材料提取的文本、转换格式、结构化数据、裁剪图像或其他派生对象进入对应 `derived/`，并引用原始 `MAT-ID`
- 材料索引记录 `MAT-ID`、原始文件名、类型、加入时间、来源 TR、内容摘要、存储路径、说明和派生关系
- 智能体的测试沙箱、运行输出、临时下载、缓存、大文件、中间副本和一次性调试对象统一进入 `.agent-project-control/runtime/`
- 当前 TR 或 PA 的长期验收证据进入其 `evidence/`；具有长期复发价值的独特最小复现进入对应 REG 的 `repro/`
- 临时对象只有在明确提升后才能离开 `runtime/`；提升时必须确定新的唯一归属，不保留无意义双份
- 清理脚本默认只处理框架明确拥有的 `runtime/`；不得根据年龄、文件名或大小自行发明全项目删除规则
- 被正式证据、材料索引、REG 或用户产物引用的对象不得作为普通垃圾删除

### 6.2.4. 例外

- 项目原生工具必须把缓存或构建输出写在固定位置时，可以保留原生位置，但必须在框架中记录边界，不为了模板一致性强行迁移
- 超大材料如果受存储或平台限制无法复制进 `materials/`，可以保存引用和摘要，但必须明确真实位置与可访问边界

**错误示例（Bad Example）**：

- 智能体把下载文件放桌面、测试数据库放项目根、日志放相邻目录、用户 PDF 又复制到三个 TR

**正确示例（Good Example）**：

- 用户 PDF 只有一个 MAT 原件；不同 TR 通过 `MAT-ID` 引用；所有一次性测试输出进入 `runtime/`，需要长期保存的证据再提升到对应 `evidence/`

**错误示例（Bad Example）**：

- 清理脚本认为“30 天前的文件都没用”，删除了唯一的长期证据

**正确示例（Good Example）**：

- 清理只作用于明确属于 `runtime/` 且没有被正式引用的对象；是否清理由当前真实条件决定，不自行发明期限

## 6.3. R22 `PROJECT.md`、`ARCHITECTURE.md`、项目 `DESIGN.md` 与共享设计基线必须分层维护；智能体基于真实项目事实和当前成熟方法学习并维护长期知识，不得复制共享规则、自动采用 Profile 或为了填模板创造事实

### 6.3.1. 原则

- `PROJECT.md`、`ARCHITECTURE.md` 和项目 `DESIGN.md` 是智能体为了长期理解当前项目而维护的项目事实层；用户默认不承担日常维护责任。
- UI/UX 设计还存在一个与项目事实不同的共享设计基线：`.agent-project-control/design/` 保存 D01–D16 共享规则、可选 Profile、来源和验证合同。共享规则回答“什么设计原则和行为合同适用”，Profile 回答“某个已认可样板有哪些精确参数和参考实现”，项目 `DESIGN.md` 只回答“当前项目采用了什么、有哪些差异与例外”。
- 三层必须保持唯一权威来源：共享 D 规则只在 `design/RULES.md`，Profile 精确参数只在 Profile/token 源，项目采用与差异只在项目 `DESIGN.md`；目标项目实际实现继续以原生源码、组件、tokens、Storybook、设计资产或既有正式文档为权威。

### 6.3.2. 触发

- 新项目首次接入框架时
- 项目目标、用户、范围、架构边界、部署方式或设计基线发生长期变化时
- 当前任务涉及界面、交互、响应、可访问性、视觉一致性、设计系统、组件行为或体验验收时
- 项目需要判断是否采用共享 Design Profile，或者现有设计与共享 D 规则发生明确差异时
- 外部成熟方法明显能够帮助智能体减少遗漏时

### 6.3.3. 必须

- `PROJECT.md` 维护项目目标、用户、问题、范围、非目标、重要约束和其他长期产品事实。
- `ARCHITECTURE.md` 维护系统边界、模块职责、依赖、数据与状态归属、运行、部署和重要跨切面事实。
- 项目 `DESIGN.md` 只维护项目设计采用状态、现有设计事实来源、当前适用 D 规则、可选 Profile 采用状态、项目差异／例外和实现来源映射；不得复制 D01–D16 完整正文或 Profile 参数表。
- UI/UX 任务先读取项目 `DESIGN.md`，再读取 `design/INDEX.md`，只加载当前任务命中的 D 规则和必要依赖；只有项目已经采用某个 Profile，或当前任务明确需要把它作为候选比较时，才读取对应 Profile 的精确参数和参考实现。
- 新项目默认 Design Profile 采用状态为 `UNRESOLVED`；APCF 自带 `tool-workbench-2.3.1` 只表示该 Profile 可用，不表示项目自动采用。只有真实项目事实、既有认可或当前用户决定支持时，才能记录 `ADOPTED` 或 `PARTIAL`。
- Profile 中的尺寸、间距、颜色角色、响应时序和其他精确值只对采用该 Profile 的适用范围成立；不得把样板值自动升级成所有项目的行业门槛或测试阈值。
- 项目已有 Design System、Design Tokens、组件库、Storybook、Figma／设计资产或等价正式文件时，优先登记和继续使用现有权威；共享基线用于路由、审查和补缺，不复制第二套实现事实。
- 智能体根据项目类型选择当前成熟且适用的产品、架构或设计方法；需要外部研究时优先使用权威来源，不凭记忆随意命名“标准框架”，也不因为某个方法存在标准章节就强迫项目填满。
- 设计变更的当前执行责任进入 Checklist 和 TEST；过程证据进入 evidence；具有长期复发价值的设计失败进入 REG；不得把每个 TR 的过程日志塞进项目 `DESIGN.md` 或共享设计规则。
- 共享设计规则或 Profile 升级时必须更新 `design/BASELINES.lock.yaml` 并运行 `design_contract.py --check`；项目没有采用受影响 Profile 时不得因为共享资源升级而自动改项目界面。

### 6.3.4. 例外

- 极小或无界面的项目确实没有独立设计层时，项目 `DESIGN.md` 可以保持 `NOT_APPLICABLE` 或极简；不得虚构视觉系统填充。
- 用户明确要求项目采用或放弃某个设计系统／Profile 时，以当前用户要求和真实项目事实为准，并记录采用范围与差异。
- 用户明确要求项目 `DESIGN.md` 成为对外正式文档时，仍保持共享规则和项目事实的职责分离，同时遵守当前用户对受众、语言与格式的要求。

**错误示例（Bad Example）**：

- 新项目因为 APCF 自带 `tool-workbench-2.3.1`，Agent 直接把 16px 间距、8px 圆角和三栏工作台改造成全站硬标准，并把 D01–D16 复制到项目 `DESIGN.md`。

**正确示例（Good Example）**：

- Agent 先调查项目现有设计系统和已认可页面；项目 `DESIGN.md` 保持真实采用状态，只引用命中的 D 规则；如果用户接受 Tool Workbench Profile，再记录 `ADOPTED/PARTIAL` 和项目差异，精确参数继续引用 Profile/token 源。

**错误示例（Bad Example）**：

- 项目已有正式 Storybook 和 tokens，Agent 为了“符合模板”在 APCF 里复制一套组件参数并要求两边同步维护。

**正确示例（Good Example）**：

- 项目 `DESIGN.md` 记录 Storybook 和 token 文件是实现事实来源；共享设计基线只提供规则与候选 Profile，组件细节继续在原项目维护。

## 6.4. R23 README 的创建、审计和实质修改必须使用 `AIALRA-0/github-readme-standardizer` 的完整技能作为唯一 README 专用标准入口；缺失时先按框架技能机制同步，不得凭智能体记忆另写一套 README 标准

### 6.4.1. 原则

- README 是项目公开入口，结构、视觉、双语同步、事实证据和发布边界容易因为不同智能体临时写法而漂移，所以 README 相关工作必须统一路由到 `AIALRA-0/github-readme-standardizer`
- README 专用技能只负责 README 领域标准；它不能替代统一写作规范，也不能扩大用户的 GitHub 写入授权

### 6.4.2. 触发

- 创建新的 README 时
- 对 README 进行结构、内容、视觉、双语、头图、链接或其他实质修改时
- 用户要求审计 README 是否符合项目统一标准时
- README 修改准备发布到远端时

### 6.4.3. 必须

- `AIALRA-0/github-readme-standardizer` 是 README 专用标准的唯一入口；不得同时维护另一套框架级 README 规则正文
- 使用技能时获取完整技能树和其明确要求的配套资源，不得只复制单个 `SKILL.md` 冒充完整安装
- 技能缺失时先通过框架技能机制解析和同步；同步失败时如实报告，不得凭模型记忆继续声称符合该技能
- README 中所有人类可读内容同时受统一写作规范接口约束；两者冲突时按更高层当前用户要求和各自职责边界处理，不自行创造第三套折中规则
- README 的事实、安装命令、截图、链接和状态必须来自当前项目实际证据；技能只能组织表达，不能创造项目事实
- 远端发布只使用当前已经存在的授权；加载 README 技能不自动获得 push、Release、PR 或其他写权限

### 6.4.4. 例外

- 纯粹逐字查看 README 且不要求审计或修改时，不需要为了读取内容先同步技能
- 用户明确指定另一套 README 标准并覆盖当前项目默认时，以当前用户要求为准，同时记录该项目例外

**错误示例（Bad Example）**：

- 技能未安装，智能体凭印象写“我知道这个 Skill 大概要求什么”，直接重写 README 并宣称符合标准

**正确示例（Good Example）**：

- 智能体先解析并读取完整技能树，再根据项目真实事实执行 README 工作；无法同步时明确停在该依赖，而不是伪造合规

**错误示例（Bad Example）**：

- 用户只授权修改本地 README，技能内部提到发布流程，智能体因此直接 push 到 GitHub

**正确示例（Good Example）**：

- README 修改完成后只停在用户授权的本地范围；外部发布权限独立判断

## 6.5. R25 所有人类可读内容必须先通过 `.agent-project-control/interfaces/WRITING_STANDARD.md` 解析当前有效写作规范，并遵守该规范当前要求

### 6.5.1. 原则

- 所有人类可读内容必须由一个可替换、可迭代的统一写作规范控制；框架不应把当前尚在演进的写作规则硬编码进每个模板，否则写作规范升级时会产生大量旧副本
- `.agent-project-control/interfaces/WRITING_STANDARD.md` 是框架发现当前正式写作规范的唯一接口，不是写作规则正文

### 6.5.2. 触发

- 创建或修改 `AGENTS.md`、规范模块、项目知识文件、执行轮次报告、REG、ADR、RB、材料说明、README 或其他面向人类阅读的正式内容时
- 写作规范接口的解析状态或正式入口发生变化时
- 正式人类可读内容准备交付前需要执行写作规范要求的复读或检查时

### 6.5.3. 必须

- 生成或修改人类可读内容以前先读取 `.agent-project-control/interfaces/WRITING_STANDARD.md`
- 当接口状态为 `RESOLVED` 时，按照接口继续读取当前正式写作规范要求的完整来源，并遵守其当前版本
- 当接口状态为 `UNRESOLVED` 时，不得声称已经遵守尚未接入的正式规范，也不得擅自绑定其他仓库、本机技能、历史草稿或模型记忆作为替代
- 写作规范要求交付前复读、检查、局部修复或其他动作时，按其当前要求执行
- 写作规范以后发生迭代时，框架通过接口切换到新版本；模板不维护平行规则副本

### 6.5.4. 例外

- 代码、机器数据、日志、逐字引用和其他对象是否需要经过写作规范，由当前正式写作规范自身决定；框架不另行复制一套例外规则
- 用户当前明确指定固定输出格式时，更高层当前用户要求优先

**错误示例（Bad Example）**：

- 写作规范尚未部署，框架把一个历史 GitHub 仓库硬编码为“正式写作 Skill”，并宣称所有模板已遵守

**正确示例（Good Example）**：

- 接口保持 `UNRESOLVED`；框架只说明尚未绑定正式入口，等正式写作规范成熟后再解析

**错误示例（Bad Example）**：

- 写作规范已经升级，只有 README 用新版本，其他模板继续保留旧规则副本

**正确示例（Good Example）**：

- 所有人类可读模板都通过同一个接口解析当前规范，升级只改变正式规范或接口解析，不逐个模板维护规则

## 6.6. R26 本框架、`AGENTS.md` 和各模板不得复制写作规范的具体规则；写作规则只在写作规范自身维护，框架只负责发现、加载、应用和复核接口

### 6.6.1. 原则

- 写作规则只能有一个权威来源；如果 `AGENTS.md`、模板、README 规范和写作接口分别复制术语、标题、标点、列表或解释规则，未来任何一次写作规范迭代都会产生互相冲突的旧副本
- 框架只负责“去哪里找到写作规范、什么时候加载、什么时候复核”，不负责重新定义“具体应该怎么写”

### 6.6.2. 触发

- 准备在框架文件中新增任何通用写作细则时
- 用户修改统一写作规范时
- 某个模板出现与正式写作规范重复或冲突的格式规则时

### 6.6.3. 必须

- `AGENTS.md`、规范模块和各模板不得复制正式写作规范中的具体术语、标题、列表、标点、大小写、解释、公式、图片或表格规则
- 框架只保存写作规范接口、加载时机、未解析状态处理和交付前复核责任
- 模板需要领域结构时可以定义“这个文件要记录什么事实”，但“这些事实具体怎样写”由正式写作规范决定
- 发现模板内存在重复写作规则时，优先删除副本并改为接口引用；不得在两个位置同步维护
- README 专用技能可以定义 README 的领域结构与验证，但共同写作表达仍由统一写作规范控制

### 6.6.4. 例外

- 当前用户在单个文件中明确要求特殊格式时，可以记录项目或任务特定例外，但不得把该例外反向升级成全局写作规范
- 机器协议、Schema、代码风格和其他非人类写作约束不属于本规则所说的写作规范副本

**错误示例（Bad Example）**：

- `AGENTS.md` 写一套术语规则，README Skill 再写一套，`TURN.md` 模板又写第三套；三个月后三套要求不同

**正确示例（Good Example）**：

- 三者只指向统一写作规范接口；各自只保存领域职责和调用时机

**错误示例（Bad Example）**：

- 为了“方便 智能体”，把当前写作规范 120 条规则复制进每个项目模板

**正确示例（Good Example）**：

- 项目模板只保留接口；需要写作时按接口加载当前正式规范

## 6.7. R27 框架只能给现有项目增加控制壳；不得为了模板整齐迁移、重排或改造原项目的源码、测试、配置和原生工具链结构

### 6.7.1. 原则

- 不同项目的源码、测试、配置、文档和部署结构已经由各自技术栈与历史形成；为了让框架看起来统一而搬动原项目，会制造无关风险并让模板反客为主，所以框架只能增加控制壳，不能强迫业务项目迁移成统一源码树
- 统一的是角色、接口和治理边界，不是每个项目的原生目录形状

### 6.7.2. 触发

- 为已有项目接入 Agent Project Control Framework 框架时
- 框架模板目录与原项目已有文件或目录命名不一致时
- 智能体准备为了“符合模板”移动源码、测试、配置或部署文件时

### 6.7.3. 必须

- 原项目源码、测试、配置、构建、部署、业务文档和资源默认保持原位
- `.agent-project-control/` 作为外层控制壳保存框架状态、历史、规则、材料、临时运行区和确定性工具
- 已有等价业务文件优先建立映射、引用或继续使用现有权威；不得仅因模板有同名文件就复制第二份事实
- 框架脚本必须能够在不改变原项目源码树的情况下工作；确实需要适配时调整框架映射，而不是优先搬项目
- 只有用户明确要求项目重构，并且该重构本身是任务目标时，才允许移动原项目结构；此时属于业务改造，不再以“框架接入”名义执行

### 6.7.4. 例外

- 新建空项目可以从模板推荐结构开始，但一旦项目形成自己的稳定结构，后续框架升级不能为了统一外观反复搬迁
- 原项目结构本身存在已确认缺陷且用户要求修复时，可以重构，但必须单独验收其业务影响

**错误示例（Bad Example）**：

- 接入框架时把现有 `src/`、`tests/`、`infra/` 全部搬到 `.agent-project-control/` 下面，只因为模板目录更统一

**正确示例（Good Example）**：

- 原项目完全不动；只增加 `AGENTS.md`、`.agent-project-control/` 和必要的技能入口，通过映射认识原有源码与测试

**错误示例（Bad Example）**：

- 项目已经有权威架构说明，框架复制一份同内容的文档并要求以后两份同时维护

**正确示例（Good Example）**：

- 框架记录现有文件是该事实的权威来源，只创建必要索引或指针

## 6.8. R28 能确定性检查的框架约束必须脚本化，并输出清晰、可定位、可修复的结果；框架结构变化后必须重新检查并生成可视化文件树

### 6.8.1. 原则

- ID 连续性、元数据存在性、索引一致性、目录结构、可见性声明和文件树生成等问题具有确定答案，不应该反复消耗模型判断；能由程序可靠检查的框架约束必须脚本化
- 确定性检查只证明它实际检查到的结构事实，不能替代语义正确性、真实功能、用户体验或正式写作规范验收

### 6.8.2. 触发

- 框架目录、规则、索引、元数据、ID、技能锁或模板结构发生变化时
- 准备发布新的框架版本时
- 需要判断两个结构化事实是否完全一致时
- 文件树变化，需要给用户或智能体查看当前结构时

### 6.8.3. 必须

- 能稳定程序判断的约束优先实现为确定性脚本，而不是增加复核者或模型投票
- 检查失败输出必须包含具体对象、失败原因和可修复位置；不得只返回笼统 `FAIL`
- 规则 ID 必须连续、唯一，并与规范模块、`AGENTS.md` 和规则索引一致
- 可见性、目录标记、技能锁、索引与引用完整性等已经脚本化的约束，修改后必须重新检查
- 框架文件树变化后自动生成 Markdown 文件树和可展开 HTML 文件树；生成物属于派生视图，不成为目录事实的第二权威
- 确定性检查脚本不得偷偷引入用户没有要求的业务阈值、质量门槛或发布条件
- 检查器自身失败时先诊断脚本、输入和环境，不得直接把产品判定为失败或要求用户手工替代所有检查

### 6.8.4. 例外

- 需要理解语义、视觉审美、用户意图或真实交互结果的问题不能因为“想自动化”就强行变成正则或静态检查
- 一次性临时诊断脚本没有长期复用价值时留在 `runtime/`，不自动升级为框架永久门禁

**错误示例（Bad Example）**：

- 为检查 R01–R31 是否缺号，新增三个模型复核者并进行多数投票

**正确示例（Good Example）**：

- 一个脚本解析规则标识并确定性验证连续性、唯一性与路由

**错误示例（Bad Example）**：

- `lint_framework.py` 返回 `FAIL`，但没有文件、行号或原因，智能体只能猜

**正确示例（Good Example）**：

- 输出具体缺失对象、冲突规则或元数据位置，并在修复后重新检查

## 6.9. R29 `REG`、`ADR`、`RB`、`MAT` 等长期单元必须使用稳定唯一 ID、创建时间戳和索引；并发创建必须由统一分配机制避免重复 ID

### 6.9.1. 原则

- IT、TR、PA、REG、ADR、RB、MAT 等长期单元需要在多个执行轮次和并行智能体之间稳定引用；如果 ID 可复用、仅靠标题识别或并发时各自猜测下一个编号，就会产生引用冲突和历史错位
- ID 表示稳定身份，时间戳表示创建时刻，标题帮助人类阅读；三者职责不同，不能互相替代

### 6.9.2. 触发

- 创建新的 IT、TR、PA、REG、ADR、RB、MAT 或其他框架长期单元时
- 两个或以上并行执行者可能同时创建同类型对象时
- 对象改名、迁移、被替代或退休时

### 6.9.3. 必须

- 每类长期对象使用稳定、项目内唯一且不回收的 ID
- 创建时记录带时区的本地时间戳；对象后续改名或状态变化不修改其原始 ID 和创建时间
- 目录或文件名可以包含 `ID + timestamp + title`，但引用关系以稳定 ID 为核心
- 并发创建必须经过统一分配机制、文件锁、原子写入或其他能够证明不会重复分配的方式；多个 PA 不得各自扫描目录后同时猜同一个“下一个 ID”
- 索引必须能够从 ID 定位到当前对象路径；路径变化时更新索引，不更换 ID
- 被替代、退休或取消的长期对象保留历史身份，不通过删除和复用编号“整理”历史

### 6.9.4. 例外

- 纯临时 `runtime/` 对象没有跨执行轮次引用价值时，不要求分配长期 ID
- 外部系统已经提供稳定不可变 ID 时，可以登记并复用外部 ID，但必须避免与框架内部命名空间冲突

**错误示例（Bad Example）**：

- PA-A 和 PA-B 同时扫描到最大 REG 为 12，两者都创建 `REG-0013`

**正确示例（Good Example）**：

- 主智能体或统一分配器原子地分配不同 ID，再把 ID 交给各 PA

**错误示例（Bad Example）**：

- `ADR-0007` 被替代后删除，后来把编号 0007 重新给另一个决策

**正确示例（Good Example）**：

- 原 ADR 保留并标记 `SUPERSEDED`；新 ADR 使用新的唯一 ID，并记录替代关系

## 6.10. R30 同一事实只能有一个唯一权威来源；其他文件只能引用或派生，不得平行维护第二份可独立漂移的事实

### 6.10.1. 原则

- 同一个事实如果在多个文件中都可以被独立修改，就会出现“每份都看起来合理但彼此不一致”的多重真相；框架必须为每类事实指定唯一权威来源，其他位置只能引用、索引或确定性派生
- 单一权威不等于所有信息都塞进一个文件；不同事实可以有不同权威来源

### 6.10.2. 触发

- 同一事实准备在第二个文件中再次完整保存时
- 索引、摘要、当前视图、生成文件或报告可能与源文件漂移时
- 恢复任务发现多个文件对当前状态给出不同答案时

### 6.10.3. 必须

- 用户原始输入以 `REQUEST.md` 为当前 TR 的权威；智能体总结只能引用，不覆盖原文
- 当前执行合同以 `CHECKLIST.md` 为权威；测试事实以 `TEST.md` 为权威；当前 TR 最终用户报告以 `TURN.md` 中冻结的最终报告为权威
- `CURRENT.md` 是当前视图，不重新维护一份独立历史；它必须从当前权威状态派生或引用
- 规则完整正文以对应规范模块为权威；`AGENTS.md` 和 `rules/INDEX.md` 的规则表面必须由规范模块生成或被确定性核对，不允许独立改写规则含义
- 代码历史以 Git 为权威；证据文件不复制整个源码树作为“备份”
- 索引只保存定位和必要摘要；完整对象正文只在对象自身权威位置维护
- 发现冲突时先确定当前真正权威，再修复派生表面；不得通过“取两边平均”产生第三个版本

### 6.10.4. 例外

- 为性能或离线使用产生的缓存、副本和生成物允许存在，但必须明确是可重建派生物，并且不能成为独立编辑入口
- 外部平台持有不可复制的真实状态时，项目文件只记录引用和已验证快照，不冒充外部状态本身

**错误示例（Bad Example）**：

- `TURN.md`、`CURRENT.md` 和聊天回复分别手写三份最终总结，后来只有一份更新了部署状态

**正确示例（Good Example）**：

- 先冻结一份 `TURN.md` 最终报告，`CURRENT.md` 和聊天回复从同一来源派生或原样复用

**错误示例（Bad Example）**：

- `rules/INDEX.md` 和规范模块各写一份完整规则说明，半年后同一个 R05 出现两个不同版本

**正确示例（Good Example）**：

- 规范模块标题与正文是权威；索引只记录 `Rule ID → module`，`AGENTS.md` 的边缘索引由脚本从规范模块同步

## 6.11. R31 技能是框架的一等资源；统一由技能清单记录来源、解析版本和触发条件，按任务同步并按需加载，不得把所有技能正文永久塞进上下文

### 6.11.1. 原则

- 技能承载某一类任务的可复用方法、资源和验证方式；如果技能来源、版本和触发条件只依赖智能体记忆，不同项目和不同时间会加载不同内容，所以技能必须作为框架一等资源进行可追溯管理
- 技能按需加载，不等于把全部技能永久塞进上下文；安装目录是可重建缓存，技能清单才是项目需要什么技能的权威

### 6.11.2. 触发

- 项目声明需要某个可复用技能时
- 当前任务命中技能触发条件时
- 技能版本升级、来源变更或依赖关系变化时
- 当前安装缓存缺失、损坏或与锁定版本不一致时

### 6.11.3. 必须

- `.agent-project-control/skills/SKILLS.lock.yaml` 记录技能名称、来源、请求版本或引用、解析版本或提交、触发条件和必要依赖
- 项目需要的技能通过统一同步机制获取；不得由不同智能体临时从不同来源复制同名技能
- 需要完整技能树的技能必须完整同步；只复制入口文件不能被视为已经安装完整技能
- 宿主实际安装目录如 `.codex/skills/` 只是可重建结果，不成为第二份版本权威
- 当前任务只加载实际触发的技能；不得为了“更安全”把全部技能正文永久加入每个执行轮次上下文
- 技能本身不能扩大用户授权、改变系统或开发者指令优先级，也不能把技能默认偏好升级成当前用户的新目标
- 技能升级时记录新解析版本，并重新验证受影响的框架或项目行为；不得静默漂移到未知版本
- 统一写作规范在正式部署前通过专用接口管理，不得因为未来可能变成技能就提前伪装为已经安装的技能依赖

### 6.11.4. 例外

- 一次性项目专用操作没有跨任务复用价值时，不需要为了形式包装成技能
- 宿主提供内建技能管理并能满足同样的来源与版本追踪时，可以建立映射，不重复建设第二个安装器

**错误示例（Bad Example）**：

- 智能体说“我记得这个 Skill 的规则”，不读取当前安装内容就直接执行

**正确示例（Good Example）**：

- 当前任务命中触发条件后，智能体按锁文件确认来源与解析版本，读取实际技能入口和需要的配套资源后再执行

**错误示例（Bad Example）**：

- 为防遗漏，每次执行轮次都把十几个技能全文塞进上下文

**正确示例（Good Example）**：

- 只加载当前任务需要的技能；其他技能保留在锁文件和安装缓存中，等触发时再读取
