# 3. 验证、证据与回归

本文件是 `03-verification-regression.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 3.1. R03 每个执行轮次必须建立独立 `TEST.md`，以一行一个 TEST-ID 的当前验收表单验证当前 Checklist，并向用户展示当前完整版本

### 3.1.1. 原则

- `TEST.md` 是当前 Turn 的验收表单，不是测试日志、Attempt 历史、跨 Turn 回归档案或调试流水；它只回答“当前候选针对当前要求现在是否通过”
- 每个 TEST-ID 只表示一个明确验收对象和验收动作，并在一行内记录当前有效状态、条件、实际操作、预期判据、实际结果和证据
- Checklist 与 TEST 不要求一一对应；一个 CL 可以由多个 TEST 从不同失效面共同证明，同一个 TEST 也可以在同一份实际证据直接证明多个 CL 时引用多个 CL
- 中途失败、重试和修复过程不原样堆入 `TEST.md`；普通过程进入当前 Turn 的 evidence 或 runtime，具有长期复发价值的重要失败提升为 REG，后续 Turn 再根据当前候选重新生成当前 TEST

### 3.1.2. 触发

- 每个新 Turn 建立 `CHECKLIST.md` 后，根据当前 CL 建立本轮 `TEST.md`
- 当前 Checklist 新增、删除、替代或改变验收边界时同步调整当前 TEST
- 实际执行测试、人工检查、真实用户路径验证或其他验收以后更新对应 TEST-ID 的当前有效结果
- 当前 TEST 失败后修复并复测时，更新同一个 TEST-ID 为当前有效结果；有价值的失败过程另存 evidence，长期失效模式提升为 REG
- 当前修改触及已有 ACTIVE REG 的根因、共享机制或适用范围时，在本轮重新建立当前回归 TEST，而不是复制旧 Turn 的 TEST 记录
- 最终交付前核对每个当前 CL 是否有足够 TEST 覆盖，以及已完成 CL 的全部适用 TEST 是否当前 PASS

### 3.1.3. 必须

- `TEST.md` 仍是当前验收唯一正文，一条当前 TEST-ID 对应一个可独立判定的验收对象；状态、CL 对应、环境、动作、判据、观察和证据不能丢失
- 新记录使用明确的 `APCF-TEST-FORMAT v3` 标记；读者可见正文必须是完整自然叙述，说明为什么验证、在何种条件下做了什么、判据与实际观察怎样比较、因此得到什么有限结论及证据在哪里；不得把五个短标签拼接成用户报告
- 解析所需事实定位只保存正文摘要与 Unicode 码点范围；事实值从同一正文读取，不允许在隐藏记录里维护“更完整但用户看不到”的另一套结果；正文变化后定位必须更新；损坏的新格式不得降级到旧格式通过
- TEST-ID 本轮唯一且稳定；同一验收对象复测更新当前状态和观察，不为每次失败新建等价身份；一个 CL 可以由多个 TEST 覆盖；一个 TEST 引用多个 CL 时必须由同一次真实检查直接证明
- 已完成 CL 的所有适用 TEST 必须当前 PASS；未执行、进行中、FAIL、BLOCKED 和不适用分别表达真实状态；因不可得结果而阻塞，不能编造观察；具有长期价值的失败保留在证据或 REG
- 实际证据必须存在、匹配当前对象与候选，并支撑正文中的观察；结构和引用检查只证明相应事实，不能自动证明自然句因果、业务正确性或用户理解程度
- 最终报告完整、同序呈现当前 TEST 正文；不得在最后交付时自由改写实际结果或只展示测试数量；状态头仅统计当前 TEST-ID，不混入历史尝试数

### 3.1.4. 例外

- 冻结 v1/v2 TEST、TURN 和证据保持原字节，兼容读取只用于历史或明确的旧格式连续任务；新生成器统一写 v3；结构兼容不等于旧报告满足本轮新要求
- 单纯调查同样可以验收来源和推理，但只声明实际核对的范围；截图、首操作或单次成功不能扩大为全状态认证
- 需要用户本人完成的验收保留 BLOCKED 或待确认；用户中止、高层指令或真实环境限制不允许被“强制通过”覆盖

**错误示例（Bad Example）**：

- `版本：当前；操作：执行；预期：通过；实际：通过；证据：已检查`，虽然字段齐全，却没有说明检查对象、判据或可核对观察

**正确示例（Good Example）**：

- `【PASS】【TEST-01】【对应 CL-02】【重新打开后的内容】：为验证上传内容可以被可靠读取，我在当前隔离版本保存文件后重新打开并逐字比较；预期读取值与原文件一致，实际比较结果为零差异，因此本次读取路径通过，逐字比较记录保存在 evidence/readback.json`

上例展示读者实际看到的正文，事实定位由编写器生成，不要求所有领域照抄固定连接词或字数

## 3.2. R06 `PASS`、`已完成`、`可用`、`已部署` 等结论必须由直接匹配当前要求、当前候选、当前版本和当前环境的真实证据支持

### 3.2.1. 原则

- 当智能体判断某项要求是否完成时，因构建成功、命令退出 `0`、测试通过、接口返回成功、页面可打开、截图存在或模型自评通过都只能证明其**实际检查过的范围**，若把局部技术信号扩大成更高层结论，就会产生“检查全绿但用户要求实际未满足”的假通过，所以任何 `已完成 / PASS / 可用 / 已修复 / 已部署 / 已验收` 结论，都必须由**直接对应当前要求、当前产物和当前版本的真实证据**支持，且结论不得超出证据实际证明的范围；

### 3.2.2. 触发

- 准备将 `CHECKLIST.md` 中任一条目标记为 `已完成` 时；
- 准备声明某个功能、问题、接口、页面、内容、部署或整轮任务通过时；
- 构建、测试、脚本、健康检查、截图、模型审核或其他检查返回成功时；
- 修改后准备继续使用历史验收结果时；
- 不同版本、环境、组件或候选分别取得通过结果时；

### 3.2.3. 必须

- 每个必需项都必须使用**直接对应该项要求**的证据，不得用间接代理指标代替；
- 每项通过必须绑定其实际适用的：
  - 产物；
  - 版本；
  - 环境；
  - 配置；
  - 必要输入；
  - 实际执行的检查；
- 必须严格区分不同层次的结论，例如：
  - 代码能够构建；
  - 程序测试通过；
  - 功能行为正确；
  - 内容或数据正确；
  - 用户真实入口可用；
  - 正式部署完成；
  - 用户本人已经验收；
- 一个检查只能支持它实际覆盖的层次；低层证据不得自动升级为高层结论；
- 不同候选、不同版本或不同环境分别取得的局部通过，不得拼接成某一个当前候选的整体通过；
- 当修改可能影响已有验收结果时，必须重新验证受影响项；未受影响且适用条件未变化的有效证据可以继续复用；
- `未执行 / 未验证 / 未知 / 失败 / 超时` 必须保持真实状态，不得为了整体全绿改写为通过；
- 自动检查与实际结果发生冲突时，必须调查冲突原因，并以真正对应用户要求的结果重新判断，不得默认采用更容易得到 `PASS` 的一方；
- 检查器或验收规则被证明错误时，可以修正判据，但必须按照修正后的正确判据重新验收；不得直接把原失败改成通过；
- 禁止通过以下方式制造完成：
  - 删除失败用例；
  - 降低原要求或阈值；
  - 换成更容易的输入；
  - 修改原始材料；
  - 人工修正自动结果后冒充系统自动成功；
  - 使用失效旧证据；
  - 用综合评分掩盖某个必需项失败；

### 3.2.4. 例外

- 用户明确只要求验证某一个技术层面时，只需对该层面作出结论，但不得将其扩大成完整产品通过；
- 某项必须由用户本人完成登录、物理操作、审美或主观签收时，智能体 可以完成自身全部可执行部分并标记为等待用户确认，但不得代替用户确认；
- 与当前修改无关，且版本、配置、环境和依赖均未改变的有效证据可以复用，不要求为了形式重新执行全部历史验收；

**错误示例（Bad Example）**：

- Build 成功；
- 327 项单元测试通过；
-智能体标记：
  - `【已完成】【正式用户入口】：功能已经完全可用；`
- 但从未实际验证正式用户入口；

**正确示例（Good Example）**：

- Build 和单元测试通过，只证明对应代码与测试范围通过；
- `【正式用户入口】` 保持未验收；
- 完成该入口对应的真实验收后，再依据实际结果更新状态；

**错误示例（Bad Example）**：

- API 请求返回 `200`；
- Agent因此声明：
  - “API 已稳定可用；”

**正确示例（Good Example）**：

- 单次 `200` 只记录为：
  - 当前输入下该次请求成功；
- 是否能够进一步声明“API 已验收”必须由后续规则规定的充分验收覆盖决定，不能从一次成功直接推导；

**错误示例（Bad Example）**：

- 自动审核模型返回 `PASS`；
- 最终正文仍存在与原材料矛盾的事实；
- Agent以审核模型的 `PASS` 为准宣布内容正确；

**正确示例（Good Example）**：

- 自动审核结果只证明该审核实际覆盖并正确判断的部分；
- 一旦发现最终产物存在事实冲突，对应 执行清单 条目立即保持失败或进行中；
- 修复实际产物并重新验证原失败点后，才能通过；

**错误示例（Bad Example）**：

- 前端版本 A 验收通过；
- 后端版本 B 验收通过；
- 当前正式候选是版本 C；
- Agent把 A、B 的结果拼起来宣布 C 整体通过；

**正确示例（Good Example）**：

- 先确定最终实际候选；
- 核对当前运行版本和组件组合；
- 对受到版本变化影响的要求重新验收；
- 只使用仍适用于当前候选的证据判断当前状态；

**错误示例（Bad Example）**：

- 用户要求：
  - “上传后刷新仍能看到文件；”
- Agent只验证上传接口返回成功，因此标记完成；

**正确示例（Good Example）**：

- 对应要求必须直接验证：
  - 上传；
  - 刷新或重新进入；
  - 重新读取；
  - 文件仍存在且内容正确；
- 只有用户要求的完整结果被实际观察到，才能标记 `已完成`；

## 3.3. R07 验收强度必须覆盖当前对象的主要失效面；单次正常路径、单个输入、单次 `200`、一次截图或一次模型判断不得冒充完整验收

### 3.3.1. 原则

- 当智能体验收一个结果时，因单次成功、单一输入、正常路径 或确定性脚本只能证明极窄场景，而真实故障往往出现在参数组合、边界值、重复操作、异常路径、状态变化、并发压力、真实用户交互和历史已知失效模式中，所以验收必须根据该功能的**真实使用方式、主要失效风险和相关历史回归**设计足够强的测试覆盖；禁止用“一次跑通”或“一类测试通过”代替对整体可靠性的验证；

### 3.3.2. 触发

- 为 `CHECKLIST.md` 中的必需项设计 `TEST.md` 时；
- 准备根据测试结果声明功能、接口、页面、流程或系统已经验收时；
- 新增或修改 API、状态逻辑、持久化、并发、外部服务、UI、用户交互或其他存在多种运行条件的功能时；
- 当前测试只覆盖单一输入、单次运行、单一环境或 正常路径 时；
- 当前修改涉及历史上曾经发生过重要失败的机制时；
-智能体准备使用“稳定”“可靠”“完整可用”“验收通过”等整体性结论时；

### 3.3.3. 必须

- 必须先根据验收对象识别**主要可能失败的维度**，再设计测试；不得先随便跑一个现成脚本，再把脚本覆盖范围当成完整需求范围；
- 除非明确不适用，验收必须考虑以下与当前对象有关的部分：
  - 正常路径；
  - 代表性输入与参数组合；
  - 边界值和极端条件；
  - 非法输入、错误路径和失败恢复；
  - 重复执行、幂等性和状态变化；
  - 保存、刷新、重启或重新读取后的持久性；
  - 多组件集成后的真实路径；
  - 并发、容量、性能、压力或长时间运行；
  - 当前实际部署环境和正式用户入口；
  - 用户真实操作和最终可见结果；
  - 与当前机制相关的历史回归；
- 测试数量不得机械固定为“跑 3 次”“跑 10 次”；必须根据风险、输入空间、状态空间和失败代价确定；
- 对存在明显参数空间的 API，不得以单次 `200` 作为完整验收；必须覆盖适用的参数组合、边界、错误输入、重复调用、状态变化以及必要的并发、负载、限流、超时和恢复；
- 对声明稳定性、吞吐量、延迟、并发能力或容量的接口，必须执行与该声明相匹配的多次运行、并发或压力测试；
- 对 UI 或网页任务，如果要求包含视觉、布局或真实交互，则必须同时覆盖：
  - 实际渲染；
  - 截图或等价真实视觉结果；
  - 用户实际点击、输入、展开、切换、刷新等适用操作；
  - 关键状态变化；
  - 相关窗口尺寸、缩放或响应式条件；
- UI 的视觉验收和交互验收不得互相替代；
- 对持久化或状态功能，不得只检查写入返回成功；必须通过适用的重新读取、刷新、重新进入或重启证明状态真实保留；
- 对非确定性模型、外部服务或概率性结果，不得用单个成功样本证明整体质量；必须使用足够多样的代表性输入和必要重复运行；
- 对修复过的缺陷，必须保留原失败场景作为回归，同时检查合理相邻场景，避免只对当前样本硬编码；
- **具有复发价值的重要失败必须沉淀为长期回归资产，不得只存在于当前聊天、当前 `TEST.md` 或智能体记忆中；**
- 长期回归资产的优先载体是：
  - 自动测试；
  - fixture；
  - regression case；
  - 可重复执行的测试数据或脚本；
- 自动化暂时不合理或无法实现，但缺陷具有高影响或高复发风险时，必须创建或更新项目 `.agent-project-control/regressions/` 中对应 REG；
- 普通一次性调试错误、临时网络抖动、单纯命令拼写错误等没有长期复发价值的问题，不进入长期回归资产；
- 当前修改触及历史回归的根因、共享机制或适用范围时，对应回归必须加入当前执行轮次的 `TEST.md`；
- `TEST.md` 必须明确记录当前选择的测试维度；重要维度或相关回归被判定为“不适用”时必须有真实理由；
- 只有对当前要求的主要失效面和相关历史回归形成足够覆盖后，才允许根据第 6 条判断对应 `CHECKLIST.md` 完成；

### 3.3.4. 例外

- 简单、纯确定性且状态空间只有单一可证明结果的任务，不需要人为制造无意义的组合、压力或重复测试；
- 与当前要求无关的风险维度不需要测试；
- 用户明确将任务限定为局部实验、Smoke 测试记录 或单次探测时，可以按该范围执行，但结论也必须限定在该范围；
- 无法执行某类必要测试时，在 `TEST.md` 中保持 `BLOCKED / 未验证`，继续完成其他可执行验收；
- 已存在稳定自动化测试完整承载某个历史回归时，对应 `REGRESSION.md` 只需保留简短根因与长期测试引用，`regressions/INDEX.md` 只保留检索摘要，不应复制完整测试步骤和日志；

**错误示例（Bad Example）**：

- 用户曾经真实遇到一个严重持久化缺陷；
- Agent修复并在当前执行轮次测试通过；
- 下一执行轮次后该失败样本只存在于聊天记录中；

**正确示例（Good Example）**：

- Agent修复根因；
- 把原失败场景加入自动回归测试；
- 在对应 `REGRESSION.md` 保留简短根因与长期测试引用，并由 `regressions/INDEX.md` 提供检索；
- 以后修改相关持久化机制时，对应测试自动进入相关验收范围；

## 3.4. R13 具有长期复发价值的重要失败必须进入索引化 REG 回归问题单元（Regression）体系；每个 REG 独立维护并优先关联可重复执行的长期测试

### 3.4.1. 原则

- 当项目出现具有复发价值的重要失败时，因 `CHECKLIST.md` 与 `TEST.md` 都属于当前执行轮次，若失败场景、根因和防复发方式只保存在当前执行轮次中，就会在换执行轮次、换智能体、重构或长期迭代后被遗忘，所以必须使用 `.agent-project-control/regressions/` 保存最小、稳定、可执行关联的历史失败体系；它是项目的长期错题本，但不是日志仓库，也不得成为新的长期待办列表
- 回归体系由 `regressions/INDEX.md` 和独立 `REG-*` 单元组成；索引只负责检索，完整历史失败正文只保存在对应 `REGRESSION.md`

### 3.4.2. 触发

- 用户实际发现并纠正了一个重要缺陷时
- 测试或审核曾经错误放过真实缺陷时
- 同一类问题已经复发时
- 一个共享根因影响多个输入、入口或组件时
- 缺陷具有较高用户影响、数据风险、费用风险、回归风险或修复成本时
- 当前修复产生了以后必须长期保护的失败场景时

### 3.4.3. 必须

- 每个长期回归问题使用独立 `REG-XXXX_<timestamp>_<title>/` 单元；目录至少包含 `REGRESSION.md`，只有存在独特历史夹具或最小复现时才增加 `repro/`
- `regressions/INDEX.md` 是项目级跨执行轮次索引；不得每个执行轮次复制一份，也不得把完整案例正文重复写入索引
- 只记录具有长期防复发价值的问题，不记录普通调试流水、临时网络波动或无长期价值的一次性操作错误
- 每个 REG 必须记录稳定唯一的 `REG-ID`、状态、对象、触发场景、原始失败、影响、根因、修复机制、适用范围、非适用范围、长期回归方式、客观通过判据、关联测试、关联执行轮次以及必要的替代或关联 REG
- `REG-ID` 必须在项目内唯一且稳定；不得通过换 ID 隐藏同一历史问题
- 状态至少区分 `ACTIVE` 与 `RETIRED`；只有对应功能、根因或适用场景已经真实消失时才能退休，不得因为很久没有复发或为了减少条目而删除历史
- 根因尚未确认时必须明确写 `UNKNOWN`，不得把猜测固化成事实
- 长期回归方式必须优先指向可以重复运行的自动测试、fixture、脚本或其他机器可执行资产；稳定自动化测试继续留在项目原生 `tests/`、`e2e/` 或等价位置，REG 只引用入口，不复制第二份测试仓库
- `repro/` 只保存无法由原生长期测试自然表达的独特历史最小复现；不得把当前源码、完整构建产物或大量日志复制进去
- 当前修改如果触及某个 `ACTIVE` REG 的根因、机制或适用范围，必须将对应回归纳入当前 `TEST.md`
- 新发现的问题如果与已有 REG 属于同一共享根因，应更新原 REG 的范围或关联关系，不得为每个表面症状重复创建新 REG
- REG 不记录当前任务是否完成，不承担未来功能计划或普通待办职责

### 3.4.4. 例外

- 没有任何符合准入条件的重要历史失败时，不需要人为编造 REG
- 一次性工具参数错误、临时网络抖动、拼写错误和无复发价值的调试噪声不进入回归体系
- 第三方系统的已知外部故障只有在项目需要长期兼容或防止错误处理时才进入回归体系
- 完全移除的功能对应 REG 可以标记 `RETIRED`，但保留历史记录，不静默删除

**错误示例（Bad Example）**：

- `regressions/INDEX.md` 直接写“REG-1 上传出过问题”“REG-2 页面有时候不对”“REG-3 昨天 API 报错了”
- 条目没有根因、触发、客观判据、长期测试入口或适用范围

**正确示例（Good Example）**：

- `REG-0014_..._文件上传持久化/REGRESSION.md` 记录：刷新后文件消失的真实触发、临时状态未持久化的根因、修复机制、标准上传持久化的适用范围、`tests/upload-persistence.spec.ts` 的长期入口，以及“刷新后文件仍存在且重新读取内容与原文件一致”的客观判据
- `regressions/INDEX.md` 只保留 `REG-ID`、状态、标题、根因摘要、范围、长期测试入口、最后验证时间和路径

**错误示例（Bad Example）**：

- 同一个持久化根因先后导致 PDF、TXT、DOCX 消失，智能体分别建立三个 REG

**正确示例（Good Example）**：

- 确认三者属于同一个持久化根因，只建立一个“文件上传持久化” REG；长期测试使用多个代表格式覆盖该共享根因

**错误示例（Bad Example）**：

- REG 已经有稳定自动化测试，`REGRESSION.md` 又复制几十行测试步骤、完整日志和输出

**正确示例（Good Example）**：

- REG 只保留触发、根因、修复、范围、客观判据和自动测试入口；详细执行逻辑只维护在测试代码中
