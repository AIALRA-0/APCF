# 1. 上下文、状态与执行轮次

本文件是 `01-context-state.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 1.1. R01 每个执行轮次开始、作用域变化、主要执行阶段变化和最终收口前，都必须重新加载当前适用规则

### 1.1.1. 原则

- 当智能体连续执行多轮任务时，因上下文增长、压缩、最近操作和旧记忆会逐渐稀释早先规则，导致格式、范围、验收和执行方式在迭代中漂移，所以每个执行轮次都必须在读取任务材料或开始实际工作前，重新读取当前作用域内全部适用的 `AGENTS.md`，并在作用域变化和最终收口时再次核对，使当前行为始终以磁盘中最新有效规则为准，而不是依赖“之前读过”的记忆；

### 1.1.2. 触发

- 每个新执行轮次开始时；
- 首次读取当前执行轮次的项目代码、计划、状态、报告或其他任务材料之前；
- 工作目录、仓库或子目录作用域发生变化时；
- 上下文压缩、会话恢复或智能体更换后；
- 适用的 `AGENTS.md` 被修改后；
- 准备最终完成判定或最终回复前；

### 1.1.3. 必须

- 每个执行轮次的第一项规则动作必须确定并完整读取当前适用的 `AGENTS.md` 链；
- 必须读取实际存在且适用的：
  - 全局 `AGENTS.md` / `AGENTS.override.md`；
  - 项目根规则；
  - 当前目录链上的更具体规则；
- 不得以“上一执行轮次已读过”“上下文里还有”“我记得内容”为由跳过；
- 进入更深目录或切换项目后，必须重新计算作用域并读取新增或变化的规则；
- 重新读取后，必须核对当前 `CHECKLIST.md` 与执行方案是否违反最新规则；冲突时先修正 执行清单 或方案，再继续工作；
- 最终回复前必须再次核对适用的 `AGENTS.md`、当前 `CHECKLIST.md` 与当前 `TEST.md`：
  - 确认规则没有因长迭代被遗忘；
  - 确认 执行清单 中所有拟标记完成的必需项均有 测试记录 中匹配且充分的验收结果；
  - 确认 测试记录 中仍存在的 `FAIL / BLOCKED / 未执行` 没有被遗漏或错误收口；
- `CHECKLIST.md` 中必须包含本执行轮次的规则读取项，例如：

  `【已完成】【规则加载】：当开始当前执行轮次时，因沿用历史规则记忆会导致约束随迭代漂移，必须重新读取当前作用域全部适用的 AGENTS.md，并以本执行轮次已完整读取实际生效的规则链确认通过；已读取：<实际规则文件>；`

- 无法读取、无法确定作用域或规则相互冲突时，不得假装已经加载；必须先解决规则来源，或只继续明确不受该未知规则影响的工作；

### 1.1.4. 例外

- 某一级目录不存在 `AGENTS.md` 时，不需要人为创建；
- 同一执行轮次内连续读取多个普通文件时，不要求每读一个文件都重复读取完全未变化的同一 `AGENTS.md`；重读边界是**新 执行轮次、作用域变化、规则变化、上下文恢复和最终收口**；
- 系统、开发者和当前用户指令优先级高于 `AGENTS.md`；重读规则不得用于覆盖更高优先级指令；
- 宿主无法访问文件系统时，必须重新读取其实际提供的等价规则入口，不得虚构已读取本地文件；

**错误示例（Bad Example）**：

-执行轮次1 已读取 `AGENTS.md`；
-执行轮次2 用户继续要求修改；
- Agent直接开始工作：
  - “前面已经读过规则，不需要再看；”

**正确示例（Good Example）**：

-执行轮次2 开始；
- Agent先重新读取当前适用的 `AGENTS.md`；
- 再建立本执行轮次的 `CHECKLIST.md`；
- 核对规则与当前要求后开始执行；

**错误示例（Bad Example）**：

-智能体在项目根读取过 `AGENTS.md`；
- 后续进入 `apps/web/`；
- `apps/web/AGENTS.md` 存在；
- Agent仍只按照根规则执行；

**正确示例（Good Example）**：

- Agent进入 `apps/web/` 后重新计算规则作用域；
- 读取新增的 `apps/web/AGENTS.md`；
- 根据更具体规则更新当前 执行清单，再继续修改；

**错误示例（Bad Example）**：

- 长任务经过多轮修复后所有测试通过；
- Agent直接最终回复；
- 但 `AGENTS.md` 还有正式入口读回要求，只是已经在长上下文中被遗忘；

**正确示例（Good Example）**：

- 测试通过后，Agent在收口前再次读取适用 `AGENTS.md`；
- 同时核对当前 `CHECKLIST.md` 与 `TEST.md`；
- 发现仍需正式入口读回；
- 完成该验收并更新 测试记录 后再最终交付；

## 1.2. R02 每个执行轮次必须建立独立 `CHECKLIST.md`，使用稳定 CL-ID 完整映射当前有效用户要求，并向用户展示当前完整版本

### 1.2.1. 原则

- `CHECKLIST.md` 是当前执行轮次的完成合同，不是跨执行轮次累积的 backlog；它只保存当前 Turn 真正承担的要求，并把每个能够独立成功或失败的结果拆成可验收条目
- 每个 Checklist 条目必须具有当前 Turn 内唯一且稳定的 CL-ID，使 TEST、报告和证据能够明确引用同一个要求；CL-ID 只表示本轮要求身份，不表示优先级，也不得跨 Turn 原样继承旧编号和旧状态
- 新 Turn 可以读取历史事实来恢复上下文，但必须根据当前用户要求和当前事实重新生成自己的 Checklist；历史完成项、旧测试、旧 backlog 和失效要求不能因为过去存在就自动进入当前表单

### 1.2.2. 触发

- 每个新的用户执行轮次开始时重新建立本轮 `CHECKLIST.md`
- 用户新增、修改、取消、冻结或恢复要求时更新对应 CL 条目
- 执行中新发现必要条件、真实阻塞或原判断失效时更新对应条目
- 测试、修复、子智能体或外部操作改变完成状态时更新对应条目
- 当前执行轮次准备结束或最终交付前重新逐项核对全部当前 CL

### 1.2.3. 必须

- 文件名统一为 `CHECKLIST.md`
- 每个执行轮次独立建立，不直接复制上一 Turn 的整张执行清单
- 当前用户要求必须全部映射到 Checklist；不得因困难、失败、耗时或暂时无方案而静默遗漏
- 执行中发现的必要条件可以加入；可选建议、顺手优化和无关历史问题不得自行升级为必需项
- 每个能够独立成功或失败的结果必须单独成项；需要不同结果才能分别判断成败时拆成不同 CL
- 每条使用统一结构：

  `【完成状态】【CL-ID】【对象】：当【触发/条件】时，因【问题/机制】会导致【后果】，必须【单一要求】，并以【客观判据】确认通过；【按需补充说明】；【按需补充完成状态说明】`

- `【完成状态】` 使用 `未开始 / 进行中 / 已完成 / 阻塞 / 不适用`
- `【CL-ID】` 使用本 Turn 内唯一稳定标识，例如 `CL-01 / CL-02`；同一条要求更新状态时不更换 CL-ID，要求被真正替代时保留当前替代关系而不是复用旧身份
- `【对象】` 必须唯一可定位，禁止“相关内容”“整体优化”等模糊对象
- `【触发/条件】` 说明要求何时成立，禁止把条件要求无差别推广
- `【问题/机制】` 与 `【后果】` 必须形成真实因果，禁止退化成无原因 TODO
- `【单一要求】` 只表达一个独立结果；如果同一结果需要多个验收维度，不必把 Checklist 拆成多个结果，可以由多个 TEST 共同验收同一个 CL
- `【客观判据】` 必须可实际观察、读取、运行或比较，禁止使用“基本正常”“应该可以”“看起来不错”等主观判断
- 完成状态由客观判据和当前 TEST 结果驱动；修改代码、执行命令、子智能体自报成功或报告生成都不能单独代表 `已完成`
- 被取消、替代或证明不适用的当轮条目不得静默消失，应标记 `不适用` 或注明替代关系
- 当前 Turn 中能完成的必需项必须尽量闭环；仍可执行的 `未开始 / 进行中 / 阻塞` 必需项不得因为“下轮继续”而主动延期
- 最终报告的 `3. 执行清单` 必须完整连续展示当前 `CHECKLIST.md` 的最新版本，不得只展示 diff、摘要或状态数量

### 1.2.4. 例外

- 简单任务可以只有一个 CL，但不得省略 Checklist
- 新 Turn 是完全不同的任务时，不继承上一 Turn 未完成事项
- 跨 Turn 继续同一稳定目标时，可以参考旧 Checklist 恢复事实，但必须重新建立当前 Turn 的 CL-ID 和当前状态
- 用户原始材料、代码、日志和引用不需要逐条改写成 Checklist；Checklist 只记录 Agent 当前承担的执行责任
- 用户明确禁止修改项目文件时，将 Checklist 保存在宿主允许的 Turn-local 状态位置，但仍向用户展示当前完整版本

**错误示例（Bad Example）**：

上一 Turn 有 `A / B / C` 三个条目；下一 Turn 用户只要求继续 B，Agent 直接复制旧 Checklist，并继续携带 A、B、C 和全部旧状态

**正确示例（Good Example）**：

Agent 读取历史事实后，根据当前请求重新建立：

- `【进行中】【CL-01】【B】：当……时，因……会导致……，必须……，并以……确认通过`

A 已完成且当前不再承担，C 当前未被要求继续，因此不自动进入新 Turn

**错误示例（Bad Example）**：

- `【已完成】【CL-02】【文件上传】：代码已经写完，测试基本正常`

**正确示例（Good Example）**：

- `【已完成】【CL-02】【文件上传】：当用户通过正式入口上传支持格式文件时，因只完成前端选择会导致页面显示成功但文件未真正保存，必须保证文件能够持久化并重新读取，并以上传成功、刷新后文件仍存在且重新读取内容与原文件一致确认通过`

这个 CL 可以由多个 TEST 分别验证上传成功、刷新后持久化和重新读取内容一致，而不是强迫一个 TEST 承担全部失效面

## 1.3. R10 恢复、继续或接管任务时，必须先重建当前真实状态；历史记录只用于恢复事实，不得自动拥有高于当前事实的优先级

### 1.3.1. 原则

- 当任务经历跨 执行轮次、上下文压缩、智能体 更换、进程中断、版本更新或长期迭代时，因历史报告、旧 执行清单、旧计划和旧“下一步”只代表当时状态，若直接继承会导致重复执行已完成动作、重新询问旧批准、使用错误版本或继续已经失效的方向，所以恢复任务时必须先重建**当前真实状态**，再从当前仍未完成的下一项继续；历史用于追溯，不得自动拥有当前事实优先级；

### 1.3.2. 触发

- 用户要求“继续”“恢复”“接着做”时；
- 新执行轮次延续之前的长任务时；
- 上下文压缩、智能体 更换、应用重启或执行中断后；
- 项目存在多个 `STATUS / DELIVERY / PLAN / CHECKLIST / TEST / handoff` 等状态记录时；
- 历史报告、当前代码、运行环境或用户最新要求出现不一致时；
- 准备重复执行一个历史上可能已经执行过的写入、部署、迁移或其他非幂等动作时；

### 1.3.3. 必须

- 恢复执行前必须确认当前：
  - 最新有效用户要求；
  - 实际工作目录和活动项目；
  - 当前代码、构建或部署版本；
  - 当前运行环境；
  - 已确认完成且不得重复的动作；
  - 当前仍未完成的必需项；
  - 当前真实阻塞；
  - 下一项可执行工作；
- 当前事实的优先级必须高于历史“下一步”；旧记录只有在重新核对后仍成立时才能继续使用；
- 历史记录之间发生冲突时，不得任选一份继续执行；必须通过当前代码、运行状态、实际对象、时间和最新有效用户要求消解冲突；
- 已经确认成功的动作不得因为换 执行轮次、换智能体或恢复上下文而重新执行；
- 已经被用户修改、取消、冻结或替代的旧要求不得重新激活；
- 历史 `CHECKLIST.md` 和 `TEST.md` 只能作为恢复参考；当前执行轮次必须按照第 2、3 条重新建立自己的 执行清单 和 测试记录；
- 恢复时必须继承已经确认的：
  - 成功事实；
  - 失败事实；
  - 有效证据；
  - 累计成本；
  - 已有授权；
  - 已知阻塞；
  
  不得把任务重置成“从零开始”；
- 对写入、部署、支付、发送、创建、删除、迁移等非幂等动作，如果中断前结果未知，必须先查目标系统实际状态或原请求回执，再决定是否重试；
- 如果历史记录已过期但仍需保留，必须明确其已被什么当前状态替代，不得让下一位智能体误认旧记录仍是当前事实；
- 发现旧状态错误时，应修正当前权威状态入口，而不是仅在新报告里写一句“以本报告为准”继续制造多个事实源；

### 1.3.4. 例外

- 用户明确要求从头重跑、重新验证或重新初始化时，可以重新执行对应部分；
- 当前状态无法可靠恢复时，可以重新验证必要事实，但必须明确这是“重新验证”，不得冒充旧证据自然延续；
- 对无副作用、成本低且重新执行比恢复状态更可靠的纯只读检查，可以重新运行，但不得因此重做无关昂贵工作；
- 历史事实仅用于审计、复盘或比较时，可以保留原样，不要求改写历史记录；

**错误示例（Bad Example）**：

- 旧 `STATUS.md` 写：
  - “等待批准部署；”
- 实际生产已经部署完成；
- 新 Agent恢复后再次询问：
  - “请确认是否允许部署；”

**正确示例（Good Example）**：

- Agent恢复后先检查：
  - 当前生产版本；
  - 实际服务状态；
  - 最新部署记录；
- 确认部署已经完成后，将旧“等待部署”视为过期状态；
- 从当前真正尚未完成的验收继续；

**错误示例（Bad Example）**：

- 上一 Agent发出了创建资源请求，但返回前断线；
- 新 Agent不知道结果，于是再次发送相同创建请求；

**正确示例（Good Example）**：

- 新 Agent先查询：
  - 原请求 ID；
  - 目标资源；
  - 实际系统状态；
- 已经创建则继承成功；
- 明确未创建后才安全重试；
- 不让上下文中断制造重复副作用；

**错误示例（Bad Example）**：

- 三周前的接管文档写着：
  - “下一步升级组件到 v2；”
- 当前仓库实际已经运行 v3；
- Agent按旧文档开始执行 v2 升级；

**正确示例（Good Example）**：

- Agent先核对当前源码、运行版本和最新有效记录；
- 确认 v2 已成为历史阶段；
- 不执行旧升级动作；
- 根据当前 v3 状态重新确定当前执行轮次的工作；

**错误示例（Bad Example）**：

- 历史 执行清单 有 20 个未完成项；
- 用户最新明确冻结其中 15 个；
- Agent恢复时直接把 20 个全部重新加入当前 执行清单；

**正确示例（Good Example）**：

- Agent读取历史只用于恢复事实；
- 结合用户最新要求重新判断当前范围；
- 只将仍然有效且当前需要继续承担的 5 项写入本执行轮次`CHECKLIST.md`；

## 1.4. R17 每个用户执行轮次必须创建独立工作区，使用项目级唯一 `TR-ID`、本地时区时间戳和简短标题，并保存原始输入、执行合同、验收账本、最终输出和证据

### 1.4.1. 原则

- 当同一项目跨多个用户消息持续迭代时，原始请求、执行解释、测试结果和最终回报若只停留在聊天上下文，会在上下文压缩、换智能体、恢复任务或并行工作后失去稳定边界，所以每个用户执行轮次必须拥有独立、可追溯的工作区
- 执行轮次工作区记录“这一次用户要求了什么、智能体承诺了什么、实际验证了什么、最终向用户报告了什么”，不能承担项目全部历史或代码版本仓库的职责

### 1.4.2. 触发

- 用户在当前项目中发送新的可执行请求时
- 用户补充、撤销或修改当前要求并形成新的用户输入时
- 上一执行轮次已经收口，用户继续同一 IT 的下一步时
- 恢复任务后收到新的用户输入并开始新的执行轮次时

### 1.4.3. 必须

- 每个执行轮次使用项目级唯一 `TR-ID`、本地时区时间戳和简短标题；ID 不回收、不复用
- 每个 TR 至少包含 `REQUEST.md`、`CHECKLIST.md`、`TEST.md`、`TURN.md` 和 `evidence/`
- `REQUEST.md` 必须逐字保存当前用户输入；智能体的解释、摘要或执行计划不得覆盖原文
- `CHECKLIST.md` 保存当前执行合同；`TEST.md` 保存当前验收账本；`TURN.md` 保存执行轮次元数据与最终用户报告；`evidence/` 只保存当前执行轮次真正需要长期引用的证据
- TR 必须关联所属 IT、开始时间、结束时间、开始与结束 Git 状态、相关规则、相关技能、相关 REG 与相关 MAT；不存在的关联明确为空，不得伪造
- 同一用户输入只创建一个主 TR；工具回调、子步骤和内部重试不额外制造新的主 TR
- 当前执行轮次产生并行智能体时，由当前 TR 的 `parallel/` 统一承载，不在项目其他位置另建平行历史

### 1.4.4. 例外

- 框架未接入或宿主明确无法写文件时，不能虚构已经创建 TR；只能使用宿主实际提供的等价记录机制，并如实说明边界
- 纯粹查看已有状态但没有形成新的项目执行轮次时，是否创建 TR 由当前项目合同决定；不得为了增加记录数量人为制造空执行轮次

**错误示例（Bad Example）**：

- 用户连续三次修改需求，智能体一直覆盖同一个 `CHECKLIST.md` 和 `TURN.md`，最后无法区分哪条要求来自哪次输入

**正确示例（Good Example）**：

- 三次用户输入分别形成 `TR-0041`、`TR-0042`、`TR-0043`；每个 TR 保留自己的 `REQUEST.md`、执行合同、测试和最终回报，同时都指向同一 IT

**错误示例（Bad Example）**：

- 一个命令失败后重试五次，智能体为五次重试创建五个主 TR

**正确示例（Good Example）**：

- 五次内部重试仍属于同一个用户执行轮次，只更新该 TR 的 `CHECKLIST.md`、`TEST.md` 和证据

## 1.5. R20 最终用户回报必须使用统一的“精确状态头 + 九段正文”合同；同一份最终报告原样保存在当前 `TURN.md`，根目录 `CURRENT.md` 由该报告确定性派生，不得分别维护互相漂移的版本

### 1.5.1. 原则

- 用户需要同时获得三层信息：完整研究与证据负责不遗漏，关键要点负责用 BP 宏观无损压缩完整讲解，行动层负责告诉用户接下来谁做什么；十区块报告只是对这三层信息架构的展开
- `CHECKLIST.md` 是当前 Turn 的执行合同，`TEST.md` 是当前 Turn 的当前验收表单；二者作为独立区块出现在完整讲解以前，用户不需要从技术正文中寻找当前承诺与当前验收结果
- 根目录 `CURRENT.md` 是当前项目入口视图；当前 TR 的 `TURN.md` 保存同一份最终报告的轮次副本；`CURRENT.md` 必须从 `TURN.md` 确定性生成
- 报告结构必须体现真实语义层级；平面内容使用无序列表，只有真实存在第二层结构时才建立继承父编号的子标题

### 1.5.2. 触发

- 当前 TR 准备向用户做阶段交付或最终收口时
- 当前结果包含代码、部署、测试、决策、研究或其他需要用户理解状态的正式工作时
- 根目录 `CURRENT.md` 需要更新为当前可恢复状态时

### 1.5.3. 必须

- 最终报告按顺序实际渲染为十个独立区块：`0. 精确状态头`、`1. 承上启下`、`2. 术语表`、`3. 执行清单`、`4. 验收记录`、`5. 完整讲解`、`6. 关键要点`、`7. 用户需要执行`、`8. 需要继续讨论、搜索或决策`、`9. 下一步推荐`
- `0. 精确状态头` 使用无序列表，一个独立状态字段一个列表项；必须显示当前 IT、当前 TR、结果状态、时间、提交或版本、真实入口、Checklist 摘要、Test 摘要、阻塞项和关键证据
- Test 摘要只统计当前 `TEST.md` 中当前 TEST-ID 的状态，例如 `PASS / FAIL / BLOCKED / 未执行 / 不适用`；不得加入 Attempt 数量、历史失败次数或上一 Turn 的测试数量
- `1. 承上启下` 默认使用 2–4 个短自然段形成清晰逻辑链，不使用项目符号；第一段交代理解本轮所需的上一状态，第二段说明为什么出现这一轮和需要解决的缺口，第三段说明本轮实际改变了什么并得到什么结果，第四段按需说明当前落点、仍未验证边界或下一阶段
- 承上启下每段只承担一个主要逻辑节点，不把上一状态、原因、变化和结果全部压进一个长复句；逻辑关系通过完整自然语言和正常连接词表达，不得使用箭头、槽位标签或短语碎片代替叙述
- 简单任务可以合并相邻逻辑节点，但最终仍应形成至少 2 个短自然段；复杂任务最多保持 4 个主要段落，细节进入后面的完整讲解
- `2. 术语表` 使用无序列表，一个术语一个列表项，只定义当前报告真正使用且用户可能不熟悉的术语
- `3. 执行清单` 完整连续展示当前 `CHECKLIST.md` 的最新版本，不得只给摘要、数量或 diff
- `4. 验收记录` 完整连续展示当前 `TEST.md` 的最新版本，一行一个当前 TEST-ID；不得附加 Attempt 历史、旧 Turn TEST、历史失败次数或执行日志，也不得用摘要替代完整当前表单
- `5. 完整讲解` 是完整报告主体，不设人为长度上限；完整解释发生了什么、为什么这样判断、候选方案、根因、实际改动、当前验证、证据、已验证结果、失败与阻塞、限制、风险、当前边界和对后续的影响
- 中途失败如果对理解根因、修改或当前边界有意义，可以在完整讲解中用自然语言说明；原始调试流水和重复执行历史仍留在 evidence/runtime，不在 TEST 或报告第 4 区块累积
- `5. 完整讲解` 只有真实需要第二层结构时才使用 `5.1.`、`5.2.` 等子标题；只有一级内容时直接使用自然段、无序列表或表格
- `6. 关键要点` 必须是对 `5. 完整讲解` 的宏观无损 BP 总结；用户只阅读本区块时，应能够知道完整讲解中的全部宏观结论、主要因果、关键结果、重要限制和未验证边界
- 每个关键 BP 使用 `- **能够单独表达该条主旨的描述性标题**：内容`；标题直接概括主旨，不机械追求四字词；正文使用一个或多个完整自然语言句子形成统一逻辑链，不得用箭头或离散短语代替语法关系
- `7. 用户需要执行` 只有一级行动时使用带描述性小标题的无序列表；只有行动内部真实存在第二层任务结构时才建立 `7.1.` 等子标题
- `8. 需要继续讨论、搜索或决策` 只有一级事项时使用带描述性小标题的无序列表；说明为什么未闭环、由谁解决、还需要什么以及关闭条件
- `9. 下一步推荐` 默认使用带描述性小标题的 BP 无序列表，并用完整自然语言句子说明做什么、为什么现在做、预期结果和进入条件
- 根目录 `CURRENT.md` 必须在每次正式收口时由当前 `TURN.md` 的最终报告重新生成；当前 TR 的 `TURN.md` 保留相同报告正文，二者必须能够确定性核对一致
- 在 Git 管理的项目中，`CURRENT.md` 指向的当前 IT/TR 可持久化子集必须同时存在并被跟踪，至少包含当前 IT 的 `ITERATION.md` 以及当前 TR 的 `TURN.md`、`CHECKLIST.md`、`TEST.md`；私有 `REQUEST.md` 和私有证据按可见性策略保存
- 最终回复用户的正文必须与当前 `TURN.md` 中冻结的最终报告一致，不得收口后临时换一套结论

### 1.5.4. 例外

- 用户当前明确要求一句话、纯数据、纯代码或其他固定输出形式时，以当前用户要求为准
- 当前任务很小，完整讲解可以相应缩短，但执行清单、当前验收表单、关键要点和真实边界不得被省略
- 宿主无法写入项目文件时，如实说明记录边界，不得虚构已同步 `TURN.md` 或 `CURRENT.md`

**错误示例（Bad Example）**：

承上启下只有一个超长句，把上一状态、本轮原因、所有改动、多个失败和下一步全部用逗号连接；验收记录又附带 A1、A2、A3 等历史失败和重试

**正确示例（Good Example）**：

## 1. 承上启下

上一轮已经完成当前状态恢复链，因此本轮不再重新设计 CURRENT 与 TURN 的持久化关系

本轮出现的原因是 TEST 仍把执行历史当成当前验收表单，导致报告随着重试不断变长，也让用户难以判断当前候选到底是否通过

这次把 TEST 恢复为一行一个当前验收结果，并允许一个 CL 由多个 TEST 从不同失效面共同证明；当前结构和报告合同已经按新模型完成验证

现在框架的确定性结构已经收敛，下一阶段进入真实项目 Pilot；真实项目尚未提供的行为证据仍明确保留为未验证边界

## 4. 验收记录

直接连续展示当前 `TEST.md` 中持久化和重新读取两项实际记录；其唯一格式权威是 R03，报告不另维护字段样例

两个 TEST 共同验收同一个 CL-02；历史调试失败没有继续堆入当前验收表单

## 1.6. R24 一个 IT 只承担一个稳定目标；同一目标下的用户变化进入新的执行轮次；目标完成、暂停、阻塞、取消或被替代时必须显式结束或切换 IT，不得静默改写旧 IT 的目标

### 1.6.1. 原则

- IT 用来表达一个稳定目标跨多个执行轮次的连续性；如果一个 IT 同时装入多个无关目标，或者用户目标变化后仍静默改写原 IT，历史就无法回答“这一阶段本来要完成什么”
- IT 不是 Sprint、日期桶或自动待办列表；它只在真实目标已经形成时创建，并以目标而不是时间长度划分

### 1.6.2. 触发

- 用户提出一个需要跨一个或多个执行轮次完成的稳定项目目标时
- 当前 IT 目标完成、暂停、阻塞、取消或被新的不同目标替代时
- 用户在同一目标上增加、收窄或修正要求，需要新 TR 继续执行时

### 1.6.3. 必须

- 一个 IT 只保存一个稳定目标及其当前有效验收条件
- 项目索引只登记真实存在的 IT；智能体不得根据“以后可能做”自行建立大量 `PLANNED` IT
- 同一目标下的新增、修正和细化通过新的 TR 记录；IT 可以更新当前有效范围，但必须保留变化来源，不把历史伪装成从未改变
- 用户要求的最终结果发生实质变化时，不得直接覆盖旧 IT 目标；应将旧 IT 标记为 `COMPLETED`、`PAUSED`、`BLOCKED`、`SUPERSEDED` 或 `CANCELLED`，再创建或切换新的 IT
- `COMPLETED` 只有在当前目标仍有效、当前验收条件满足、必要测试与回归通过、适用的真实环境已经验证，并且没有仍属于该目标的未完成要求时才能使用
- IT 状态和目标变化必须能够追溯到相关 TR 与证据

### 1.6.4. 例外

- 一次极小、单轮即可完成且项目不需要长期目标追踪的工作，可以由框架初始化策略决定是否创建独立 IT；不得为了形式人为制造空目标
- 用户明确要求并行维护多个独立目标时，可以存在多个非完成 IT，但每个目标仍保持独立；当前实现若只支持单个 `ACTIVE` IT，必须如实遵守该实现边界，不通过改写目标规避

**错误示例（Bad Example）**：

- IT-0042 原目标是“修文件树”；用户后来要求“重做认证”，智能体直接把 IT-0042 标题改成“重做认证”，历史上看不到原目标

**正确示例（Good Example）**：

- 原 IT 按事实标记 `COMPLETED`、`PAUSED` 或 `SUPERSEDED`；认证工作创建新的 IT，当前用户输入的 TR 记录目标切换

**错误示例（Bad Example）**：

- 智能体自己想到十个“以后可以优化”的方向，自动生成十个 `PLANNED` IT

**正确示例（Good Example）**：

- IT 索引只登记用户已经形成的真实目标；候选建议留在当前报告的下一步推荐，不自动升级成项目义务
