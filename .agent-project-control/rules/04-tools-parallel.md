# 4. 授权、工具与并行

本文件是 `04-tools-parallel.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 4.1. R08 已经授予且仍有效的授权必须持续继承；局部账号、凭证、网络、外部服务或第三方平台故障只能影响被证据证明受影响的路径

### 4.1.1. 原则

- 当用户已经授权某项任务时，因修复、重试、候选版本变化、智能体 切换或局部外部故障并不会自动改变原授权范围，若反复索要相同授权或把一个账号、服务、请求的失败扩大成整个任务不可执行，就会制造无意义等待并把本可自主完成的工作重新推给用户，所以必须持续继承仍然有效的授权，并把权限、认证、资源和故障严格限制在其实际影响范围内；

### 4.1.2. 触发

- 已授权任务进入修复、复测、重试或下一执行阶段时；
- 候选版本、实现方式、智能体 或会话发生变化时；
- 外部 API、提供方、账号、凭证、网络、权限、额度或其他资源发生异常时；
- 外部写入、部署或付费请求结果未知时；
-智能体准备再次向用户请求已经给过的批准时；

### 4.1.3. 必须

- 同一任务范围内已经明确授予的授权必须持续有效，不得因普通修复、可逆实现调整、重试、版本变化或智能体更换而重复索要；
- 遇到外部异常时，必须分别判断：
  - 当前动作是否已获授权；
  - 凭证是否存在；
  - 凭证是否有效；
  - 认证是否成功；
  - 目标对象是否具有权限；
  - 服务是否可达；
  - 资源或额度是否真实不足；
  - 请求是否已经发送；
  - 请求结果是明确失败、明确成功还是未知；
- 一个账号、提供方、接口、凭证或网络路径失败，只能证明该具体路径当前存在问题；不得在没有验证的情况下宣布所有账号、所有线路、所有能力或整个任务不可用；
- 可替代路径仍在原授权和范围内时，应调查并使用适用的替代路径，而不是立即返回用户；
- 认证、凭证缓存、配置或本地状态错误能够由智能体修复时，必须先修系统，不得把内部故障转化成要求用户重复授权；
- 外部写操作结果未知时，必须优先查询原请求、目标对象或实际状态；不得直接重发可能产生重复副作用的操作；
- 恢复或更换智能体后，必须保留：
  - 已确认的授权；
  - 已成功动作；
  - 已发生费用；
  - 已确认外部状态；
  
  不得重新初始化成“尚未授权 / 尚未执行”；
- 只有真正超出原授权边界的事项才可以重新询问用户；

### 4.1.4. 例外

- 以下情况属于新的授权边界，可以重新询问用户：
  - 新增任务范围；
  - 新增或明显增加费用；
  - 新的数据发送目标或隐私边界；
  - 新的不可逆、破坏性或明显高风险操作；
  - 用户此前明确保留给本人决定的事项；
  - 原授权明确设置了时间、次数、对象或范围限制且当前已经超出；
- 原授权已经被用户撤销、替代或明确过期时，不得继续沿用；
- 安全或宿主规则要求重新确认时，应服从更高优先级约束；

**错误示例（Bad Example）**：

- 用户已经授权：
  - 修复并部署当前版本；
- 第一次部署失败；
- Agent问：
  - “部署失败了，请确认是否允许我修复后再次部署；”

**正确示例（Good Example）**：

- 原部署授权仍覆盖当前任务；
- Agent定位部署失败原因；
- 在原授权范围内修复并重新验证；
- 只有发现需要执行原授权之外的新高风险动作时，才重新询问用户；

**错误示例（Bad Example）**：

-提供方A 返回一次额度错误；
- Agent直接宣布：
  - “模型服务不可用，请充值后再继续；”
- 没有检查实际使用的账号、提供方 B、当前凭证或请求状态；

**正确示例（Good Example）**：

- Agent先确定失败发生在哪个具体账号和线路；
- 分别核对认证、额度、当前配置和其他已授权路径；
- 只把被证据证明不可用的路径标记失败；
- 其他仍可工作的路径和不依赖该提供方的任务继续执行；

**错误示例（Bad Example）**：

- 用户已经更新凭证；
- 系统仍从旧缓存读取旧 Token；
- Agent再次要求：
  - “请重新授权账号；”

**正确示例（Good Example）**：

- Agent确认用户授权和新凭证已经存在；
- 定位旧缓存或配置读取问题；
- 修复系统状态后重新认证；
- 不要求用户为智能体自己的状态错误重复授权；

**错误示例（Bad Example）**：

- 发布请求发出后连接中断；
- Agent无法确定请求是否已经成功；
- Agent立即再次发送相同发布请求；

**正确示例（Good Example）**：

- Agent先将结果标记为 `Unknown`；
- 查询目标系统、请求 ID、实际版本或对象状态；
- 确认第一次操作没有生效后，才决定是否安全重试；
- 如果已经成功，则直接继承成功状态，不产生重复写入；

## 4.2. R09 交互测试必须选择满足验收目标的最低侵入方式；工具失败必须先自诊断，不得因一次报错直接宣称工具不可用或把工作推给用户

### 4.2.1. 原则

- 当智能体需要通过浏览器、桌面、GUI、MCP 或其他交互工具执行测试时，因用户可能同时使用同一台设备，而鼠标、键盘、主屏幕、浏览器会话和前台窗口都属于会被争用的共享资源，且单个自动化入口的报错也不代表该工具或能力真实不可用，所以必须优先选择**不抢占用户交互资源、可隔离、可后台执行**的测试方式；只有必要时才能升级到会影响用户前台操作的方式，并且任何工具失败都必须经过合理诊断后才能判定不可用或切换路径；

### 4.2.2. 触发

- 需要进行网页、桌面、GUI、真实用户交互或 CUA 测试时；
- 测试方式可能控制鼠标、键盘、焦点、窗口、剪贴板或主屏幕时；
- 需要打开外部浏览器、桌面窗口或其他可能干扰用户工作的界面时；
- Playwright、MCP、内置浏览器、远程浏览器、CUA 或其他自动化工具出现连接、认证、超时、会话或调用错误时；
-智能体准备因为某个工具报错而切换到更侵入性的测试路径时；

### 4.2.3. 必须

- 测试方式必须按**满足验收要求所需的最低侵入性**选择，优先级原则为：
  - 无 GUI 的确定性检查、API、脚本或程序化验证；
  - 不抢占用户鼠标、键盘和前台焦点的隔离浏览器或自动化会话；
  - 独立窗口、独立浏览器 Profile、独立桌面或其他可隔离的交互环境；
  - 只有前述方式无法完成必要验收时，才使用会直接控制用户当前桌面的 CUA 或前台 GUI 操作；
- 不得仅因为 CUA “更真实”就优先使用会抢占用户鼠标或键盘的方案；能够使用不干扰用户的方式完成相同验收时，必须使用较低侵入方案；
- 使用浏览器自动化时，应优先使用与用户当前工作会话隔离的浏览器、Context、Profile、窗口或等价机制，避免修改、抢焦点或污染用户正在使用的页面状态；
- 不得反复把测试窗口强制弹到用户主屏幕前台、抢夺输入焦点或持续覆盖用户正在操作的窗口；如果工具本身会产生这种行为，应优先寻找后台、隔离或其他等价测试路径；
- 用户明确表示当前正在使用鼠标、键盘、浏览器、GPU、设备或其他共享资源时，必须尊重该占用：
  - 停止会冲突的操作；
  - 继续不依赖该资源的测试或工作；
  - 不得把“不能抢用户资源”解释成“整个测试无法继续”；
- 某个测试工具或自动化入口第一次报错时，不得立即宣称“不可用”；
- 工具报错后必须先区分并调查至少与当前现象相关的：
  - 工具本身是否启动；
  - 当前连接或会话是否仍有效；
  - 参数、端点、端口或调用方式是否正确；
  - 认证或权限是否有效；
  - 当前错误是瞬时失败还是稳定复现；
  - 是否存在同一工具的其他合法入口；
  - 是否只是当前页面、会话或环境状态异常；
- 对一次超时、连接失败、MCP 调用错误、Playwright 连接失败或浏览器异常，不得直接推导：
  - 整个工具不可用；
  - 所有浏览器自动化不可用；
  - 必须改用人工前台操作；
  - 必须让用户介入；
- 在切换测试方式前，必须说明当前方式具体缺少什么能力；不得因为没有调查一个错误，就逐级切换到越来越侵入用户环境的工具；
- 如果一个工具确实不可用，应选择**能够满足同一验收目标的最小侵入替代路径**，而不是默认选择最容易控制用户主桌面的方案；
- CUA 或前台 GUI 确实是必要的唯一验收方式时，必须：
  - 将操作限制在必要步骤；
  - 避免无关窗口和重复弹窗；
  - 不操作用户无关应用或标签；
  - 完成必要交互后立即释放鼠标、键盘、焦点和窗口控制；
- `TEST.md` 中必须记录实际使用的测试方式和环境，使“后台自动化通过”和“真实前台人工/CUA验证”不会被混为同一种证据；

### 4.2.4. 例外

- 用户明确要求智能体使用指定浏览器、CUA、真实桌面或当前前台会话进行测试时，可以按用户指定方式执行；
- 某项需求本身就是验证真实系统级鼠标、键盘、拖拽、原生窗口、文件选择器或其他无法由隔离自动化等价模拟的行为时，可以使用 CUA 或前台 GUI，但只限必要范围；
- 只有用户本人持有且无法隔离复制的登录态、硬件、设备或操作环境才能完成验收时，可以请求用户介入，但必须先完成所有不依赖用户前台操作的验证；
- 工具已经通过明确、可复现的检查确认不可用时，不要求无限重试；应保留错误并采用下一种最低侵入的有效路径；

**错误示例（Bad Example）**：

- 需要测试网页按钮；
- Agent直接启动控制用户当前桌面的 CUA；
- 鼠标不断被智能体抢走，用户无法继续工作；

**正确示例（Good Example）**：

- 先判断按钮行为是否能在隔离浏览器自动化中真实验证；
- 使用独立自动化会话完成点击、状态变化和结果读取；
- 只有必须验证真实桌面特有行为时才升级到 CUA；

**错误示例（Bad Example）**：

- 内置浏览器第一次连接报错；
- Agent立即认为：
  - “内置浏览器不可用；”
- 随后不断启动外部浏览器窗口，并把窗口弹到用户主屏幕测试；

**正确示例（Good Example）**：

- 先检查内置浏览器的连接、会话、参数和当前环境；
- 能恢复则继续使用隔离方式；
- 确实不可用后，再选择下一种能够满足验收的最小侵入方案；
- 不因为一次工具错误直接升级为干扰用户主桌面的方案；

**错误示例（Bad Example）**：

- Playwright/MCP 返回一次超时；
- Agent写入：
  - `BLOCKED：Playwright 不可用；`
- 随后要求用户手动测试；

**正确示例（Good Example）**：

- 保持该项 `进行中`；
- 检查 MCP 服务、浏览器连接、实际端点、会话和调用参数；
- 用最小操作复现；
- 如果工具恢复，继续自动验收；
- 只有确认该路径真实不可用且不存在当前可执行的低侵入替代方式后，才标记相应阻塞；

**错误示例（Bad Example）**：

- 用户说：
  - “别抢我的鼠标，我还要工作；”
- Agent停止 CUA 后直接结束整轮测试；

**正确示例（Good Example）**：

- Agent立即停止会争抢鼠标的操作；
- 改用后台脚本、隔离浏览器、API 或其他不冲突路径完成能够完成的测试；
- 只有确实必须依赖真实前台交互的剩余验收才等待合适窗口或用户介入；

**错误示例（Bad Example）**：

- 外部浏览器已经能后台完成测试；
- Agent仍反复激活窗口、置顶、切标签和抢焦点，因为这样“更方便观察”；

**正确示例（Good Example）**：

- 保持测试窗口隔离或后台运行；
- 只读取必要截图、DOM、日志或测试结果；
- 不让测试工具的便利性凌驾于用户正常使用设备的权利之上；

## 4.3. R11 可独立工作优先使用多个低成本并行智能体执行；必须隔离代码、数据、浏览器、账号、端口、进程、设备、额度和部署目标；主智能体始终承担整合与最终责任

### 4.3.1. 原则

- 当智能体使用子智能体、并行任务或多个执行环境时，因串行执行会浪费可并行工作的吞吐量，而无边界并行又会造成数据库、浏览器会话、账号、端口、GPU、磁盘、模型额度和部署目标等共享资源争用，所以必须将**可独立工作优先拆给多个廉价子智能体并行执行**，同时明确职责和资源边界；高级智能体应主要承担需求理解、关键判断、冲突裁决、结果整合和最终验收，从而在不牺牲正确性的前提下提高并行度、速度和成本效率；

### 4.3.2. 触发

- 使用一个或多个子智能体时；
- 同时存在多个可以独立推进的实现、测试、调查、分析或修复任务时；
- 当前存在大量确定性、机械性或容易独立验收的工作时；
- 多个任务可能访问同一代码、数据、账号、浏览器、端口、设备、服务或部署环境时；
- 子智能体返回结果并准备合并时；
- 高级智能体准备亲自串行执行大量可以安全委派的工作时；
- 准备根据多个子任务结果判断整轮完成时；

### 4.3.3. 必须

- 在宿主提供可用子智能体且任务可以安全拆分时，必须默认积极使用多个廉价子智能体并行执行独立工作，优先使用如 **Luna Max 或当时可用的其他低成本执行 智能体**；不得让高级智能体长时间串行承担大量能够安全委派的机械工作；
- 当存在多个互不依赖的工作项时，必须优先考虑**同时启动多个子智能体**，而不是让一个智能体逐项串行执行；
- 并行数量必须根据：
  - 任务独立性；
  - 共享资源；
  - 宿主并发限制；
  - 上下文和协调成本；
  - 实际速度与成本收益；
  
  动态决定，不机械追求智能体数量；
- 高级智能体应优先承担需要较强全局理解和判断能力的工作，例如：
  - 理解和冻结用户真实目标；
  - 任务拆分与依赖判断；
  - 架构与关键技术决策；
  - 高不确定性问题诊断；
  - 风险、权限和范围判断；
  - 子智能体结果冲突裁决；
  - 跨模块整合；
  - 最终验收与完成判定；
- 可重复、确定性高、容易独立验证的工作应优先委派给廉价子智能体，例如：
  - 独立代码修改；
  - 代码和文件调查；
  - 测试执行；
  - 日志分析；
  - 批量机械处理；
  - 独立审查；
  - 数据整理；
  - 多个互不依赖的复现任务；
  - 多方案并行验证；
- 对同一个高不确定性问题，在成本合理且独立观点有价值时，可以并行调用多个廉价子智能体独立调查、复现或提出方案，再由主智能体根据实际证据裁决；
- 多个子智能体得出相同结论只能提高调查可信度，**不得把“多个智能体都这么说”本身当成事实证据**；
- 并行前必须明确每个任务的：
  - 目标；
  - 修改或读取对象；
  - 写入权限；
  - 依赖；
  - 共享资源；
  - 最终负责人；
- 独立任务优先并行；存在写入冲突、强顺序依赖或共享状态竞争的任务不得无隔离并发执行；
- 除代码文件外，还必须识别并保护可能冲突的：
  - 数据库与测试数据；
  - 浏览器 Profile、登录态和页面会话；
  - 账号和凭证；
  - 端口和后台进程；
  - GPU、设备和磁盘；
  - 模型额度与付费资源；
  - 构建产物、镜像和部署目标；
- 多个智能体不得未经协调修改同一可变对象；需要共同写入时必须使用项目已有的锁、事务、工作树、命名空间或其他隔离机制；
- 子智能体的使用必须以**提高有效吞吐量**为目的：
  - 不得把同一个简单任务无意义复制给大量 智能体；
  - 不得让多个智能体重复做完全相同且没有独立比较价值的工作；
  - 不得为了增加并行数量制造额外协调成本；
  - 不得让并行造成的资源竞争超过其速度收益；
- 如果廉价子智能体无法可靠完成某项工作，主智能体必须先判断失败原因：
  - 若任务范围过大，则进一步拆小；
  - 若上下文不足，则补充必要上下文；
  - 若单个智能体执行失败，可换其他廉价子智能体；
  - 若问题适合独立比较，可并行交给多个廉价子智能体；
  - 只有确认任务本身确实需要更强全局判断时，才升级给高级智能体；
- 不得因为一个廉价子智能体一次失败，就默认所有剩余工作都必须由最高成本智能体亲自执行；
- 子智能体的 `PASS` 只代表其负责范围；主智能体必须检查其实际产物和证据，不得直接把自报状态当成最终事实；
- **委派执行，不委派最终责任；** 主智能体始终对：
  - 任务是否完整；
  - 子任务是否冲突；
  - 结果是否真正整合；
  - 最终候选是否通过；
  
  承担责任；
- 合并多个子任务后，必须针对**整合后的最终候选**执行受影响的必要回归，确认局部正确没有在组合后失效；
- 某个并行任务失败或受阻时，只影响依赖它的任务；其他独立任务继续执行；
- 并行造成的超时、资源争用或测试噪声必须与真实产品故障区分；不得因为单独重跑通过就自动宣布生产环境稳定；
- 当前执行轮次的 `CHECKLIST.md` 和 `TEST.md` 必须反映最终整合状态，而不是停留在各子智能体的局部结果；

### 4.3.4. 例外

- 完全只读、互不影响的调查可以直接并行，不需要人为增加复杂的资源隔离；
- 当任务无法安全拆分、存在强顺序依赖、多个智能体会争用同一不可隔离资源，或并行协调成本明显高于收益时，可以降低并行度或由单一智能体执行；
- 项目已有可靠的事务、锁、隔离环境或并行执行机制时，优先复用现有机制，不重复发明新的协调层；
- 必须串行的迁移、部署、唯一写入或其他具有严格顺序要求的动作可以保持串行，不得为了提高并发强行拆分；
- 涉及关键架构、安全、不可逆操作、复杂冲突裁决或必须依赖完整全局上下文的工作，不应仅为了降低成本而强行交给能力不足的子智能体；
- 宿主没有提供廉价子智能体、并发槽位不足或实际模型能力与成本结构发生变化时，应按当前真实能力选择执行者，不得虚构 Luna、Max 或其他智能体可用；
- 用户明确限制只能使用单一执行者或禁止并行时，遵守该边界；

**错误示例（Bad Example）**：

- 当前有 8 个彼此独立的代码检查和测试任务；
- 高级智能体自己逐个读取文件、逐个运行测试、逐个整理日志；
- Luna / Max 子智能体全程闲置；

**正确示例（Good Example）**：

- 主智能体先判断依赖和资源冲突；
- 将 8 个独立工作拆给多个 Luna / Max 子智能体并行执行；
- 主智能体同时处理架构判断和高风险问题；
- 子智能体返回后，主智能体整合结果、处理冲突并完成最终验收；

**错误示例（Bad Example）**：

- 一个任务包含：
  - 20 个独立模块的静态检查；
  - 1 个关键架构决策；
- 高级智能体自己串行完成全部 21 项；

**正确示例（Good Example）**：

- 多个廉价子智能体并行完成 20 个确定性检查；
- 高级智能体聚焦关键架构决策；
- 子智能体的事实调查结果汇总后，由高级智能体根据证据完成最终判断；

**错误示例（Bad Example）**：

- 一个 Luna 子智能体第一次修改失败；
- 主 Agent立即认为廉价模型能力不足；
- 后续所有机械工作全部收回，由高级智能体串行执行；

**正确示例（Good Example）**：

- 主 Agent先判断失败原因；
- 如果任务过大：
  - 拆小后重新委派；
- 如果上下文不足：
  - 补充最小必要信息后重新委派；
- 如果需要独立比较：
  - 并行调用多个廉价子智能体；
- 只有确认该问题真正需要高级推理和全局判断时，才由高级 Agent接管；

**错误示例（Bad Example）**：

-智能体A 修改前端；
-智能体B 修改后端；
- 两者同时重置同一个测试数据库；
- A、B 分别报告测试通过；
- 主 Agent直接宣布整体完成；

**正确示例（Good Example）**：

- A、B 的源码职责独立；
- 测试数据采用独立对象或隔离环境；
- 两侧完成后合入同一最终候选；
- 主 Agent针对整合后的前后端真实链路重新验收；
- 整体结果通过后再完成 执行清单；

**错误示例（Bad Example）**：

- 两个子智能体同时操作同一个浏览器登录态；
- 一个切换账号，另一个继续执行原测试；
- 两边最终都报告 `PASS`；

**正确示例（Good Example）**：

- 并行前明确浏览器会话归属；
- 为不同测试使用隔离 Context / Profile，或让必须共享会话的操作串行；
- 每项证据绑定实际使用的账号和会话；

**错误示例（Bad Example）**：

- 子智能体B 返回：
  - “功能已完成，全部测试通过；”
- 主 Agent没有检查代码、版本和测试证据，直接把主 执行清单 标记 `已完成`；

**正确示例（Good Example）**：

- 主 Agent读取 B 的实际产物和 测试记录 结果；
- 确认版本、范围和证据符合本轮要求；
- 合并后运行受影响的整合测试；
- 只有最终候选通过后才更新主 执行清单；

**错误示例（Bad Example）**：

- GPU 被另一个任务占用；
- Agent因此把所有并行工作全部暂停；

**正确示例（Good Example）**：

- 只暂停依赖 GPU 的任务；
- 继续并行完成代码检查、CPU 测试、调查、文档准备和其他不依赖 GPU 的必需工作；
- GPU 可用后再恢复受影响分支；

## 4.4. R18 PA 并行智能体（Parallel Agent）必须作为当前执行轮次下的小型执行轮次存入 `parallel/`；最多允许一层 PA，PA 不得继续创建下一层智能体

### 4.4.1. 原则

- 并行智能体用于把清晰、独立、资源可隔离的工作并发处理，不用于无限递归分发任务；如果子智能体继续创建子智能体，主智能体会失去资源所有权、任务回收、证据整合和停止条件的可见性，所以本框架只允许一层 PA
- PA 是当前主 TR 的子执行单元，不是新的项目主执行轮次；其结构与 TR 相似，是为了让输入、执行、测试和结果都可追溯

### 4.4.2. 触发

- 当前 TR 存在两个或以上可以独立推进且不会争抢同一写入面的子任务时
- 机械搜索、独立调查、互不冲突的文件修改或隔离测试可以降低主智能体成本和等待时间时
- 需要让不同智能体分别验证独立假设，但最终仍由主智能体综合判断时

### 4.4.3. 必须

- PA 只能通过统一创建机制进入当前 TR 的 `parallel/PA-XXXX_<timestamp>_<title>/`
- 每个 PA 至少保存 `REQUEST.md`、`CHECKLIST.md`、`TEST.md`、`TURN.md` 和 `evidence/`
- PA 必须明确父 TR、任务边界、输入、允许写入的文件或资源、禁止触碰的资源和回收条件
- PA 不得拥有自己的 `parallel/`，不得继续创建任何下一层智能体
- 主智能体统一分配 PA ID，并在开始前处理文件、数据库、浏览器、账号、端口、进程、设备、额度和部署目标的资源冲突
- PA 的自报 `PASS` 只能证明其局部范围；主智能体必须读取实际产物和证据、处理冲突，并对整合候选执行必要验收
- 一个子任务如果需要频繁共享同一可变状态、不断互相等待或反复合并冲突，就不应为了“看起来并行”强行拆成 PA

### 4.4.4. 例外

- 当前环境不支持并行智能体时，主智能体顺序完成任务，不得假装已经并行
- 共享资源无法安全隔离时，相关工作顺序执行；不能为了追求速度牺牲状态正确性

**错误示例（Bad Example）**：

- PA-A 创建 PA-A-1，PA-A-1 再创建 PA-A-1-a；主智能体不知道还有多少任务和进程在运行

**正确示例（Good Example）**：

- 主 TR 创建 PA-A、PA-B、PA-C 三个一层子执行单元；每个 PA 结束后回传实际产物和证据，由主智能体统一整合

**错误示例（Bad Example）**：

- 两个 PA 同时修改同一个配置文件和同一个数据库记录，最后以“谁最后写入”为准

**正确示例（Good Example）**：

- 主智能体先划分文件与资源所有权；不能隔离的共享写入由一个执行者负责，其他 PA 只读或顺序执行
