# 2. 执行范围、目标与根因

本文件是 `02-execution-scope.md` 中规则完整正文的唯一权威来源；`AGENTS.md` 与 `rules/INDEX.md` 只负责路由或派生索引，不得独立维护第二份规则正文

## 2.1. R04 已授权任务不得停在仍可由智能体推进的中间状态；失败后继续定位、修复和复验，直到完成或满足真实停止条件

### 2.1.1. 原则

- 当用户已经授权执行一项任务时，因用户要的是**任务结果**而不是一次尝试、一个阶段、一份报告或一个 `Partial / Failed` 状态，所以只要当前执行轮次仍存在属于本轮范围、已经授权且智能体可以继续推进的必需工作，就必须继续执行；中间状态只能改变 `CHECKLIST.md` 中的进度，不能自动把执行责任交还给用户；

### 2.1.2. 触发

- 用户要求实现、修改、修复、测试、验证、部署、迁移、清理、调试或其他实际执行任务时；
- 阶段、测试、工具调用或子智能体返回后，仍有必需项未完成时；
- 出现 `Failed / Partial / Blocked / Unknown` 等非完整通过状态时；
-智能体准备结束当前 执行轮次，而 `CHECKLIST.md` 仍存在未完成必需项时；

### 2.1.3. 必须

- 必须以**本轮最终要求是否满足**判断完成，不得以代码写完、测试跑完、阶段结束、报告生成或子智能体返回判断完成；
- 每次阶段、测试、工具或子智能体返回后，必须回到 `CHECKLIST.md` 检查剩余必需项并继续下一项可执行工作；
- 可修失败必须继续执行“**定位 → 修复 → 复验**”，不得只报告失败原因和下一步；
- 当测试、验收或实际操作失败时，不得仅将对应 执行清单 条目标记为 `未完成 / 阻塞` 后返回用户；只要失败原因仍可由智能体调查、定位、修复或进一步验证，就必须继续处理，直到该项通过或满足真实停止条件；
- `未完成` 只是当前状态，不是停止理由；`阻塞` 只能用于已经严格确认智能体当前确实无法自行解除的条件，不得把“尚未调查”“尚未定位”“尚未尝试修复”或“一次测试刚失败”标记为阻塞；
- 第一次修复失败后，只要仍存在合理调查路径，就必须依据新证据继续定位或改变修复方法；不得因为一次或数次尝试失败，就默认把问题交回用户；
- 同一授权范围内仍有可执行工作时，不得要求用户再次回复“继续”“确认继续”或重新授权；
- 主智能体必须承接子智能体的结果、失败和剩余工作，并对整轮最终完成负责；
- 进度汇报可以发送，但汇报后任务仍继续执行；进度消息不得成为隐式停机点；
- 当前执行轮次能完成的必需工作不得主动写成“下一执行轮次再做”；

### 2.1.4. 例外

- 用户明确只要求调查、规划、审查、解释等非实施任务时，对应产物就是本轮终点；
- 用户明确要求“做到这里停止”“本阶段完成后回来”时，按该边界结束，不进入下一阶段；
- 用户明确取消任务时停止；
- 剩余工作确实满足后续规定的真实停止条件时，可以例外结束，但必须先完成所有仍可独立推进的必需工作；
- **当所有剩余必需项都必须由用户介入后才能继续时，可以返回用户，但必须严格确认：**
  - 不存在任何仍可由智能体独立完成的实现、调查、修复、验证、准备或收尾工作；
  - 每个剩余项都存在明确、具体且真实的用户依赖，而不是笼统的“需要确认”；
  - 用户需要执行或决定的动作必须是智能体当前权限或能力确实无法代替的；
  - 该用户动作完成后，任务存在明确的继续路径；
  - 返回前必须把所有不依赖用户的工作做到当前可达到的终点，并在 `CHECKLIST.md` 中准确记录等待用户的对象、原因和恢复条件；
- 不得以本规则为理由重新打开已冻结、已排除或未授权的历史事项；

**错误示例（Bad Example）**：

- 用户要求修复 5 个问题并验证；
-智能体完成 3 个，剩余 2 个测试失败；
-智能体回复：“3/5 已通过，另外两个原因已找到，如需继续我可以下一轮修复；”

**正确示例（Good Example）**：

- 用户要求修复 5 个问题并验证；
-智能体完成 3 个，剩余 2 个测试失败；
- Agent继续定位、修复、复验剩余两项；
- 只有 5 项全部达到本轮验收，或剩余项出现真实停止条件后，才结束当前 执行轮次；

**错误示例（Bad Example）**：

- API 测试第一次失败；
-智能体将 执行清单 更新为：
  - `【未完成】【API】：测试失败；`
- 随后回复：
  - “API 尚未通过，需要后续继续调查；”

**正确示例（Good Example）**：

- API 测试第一次失败；
-智能体保持该项 `进行中`；
- 继续读取错误、复现失败、定位原因、实施修复并重新测试；
- 如果再次失败，则依据新的失败信息改变诊断或修复方法；
- 只有通过客观验收，或严格确认存在当前无法解除的真实阻塞后，才改为 `已完成` 或 `阻塞`；

**错误示例（Bad Example）**：

- 三个子智能体分别返回：
  - A：通过；
  - B：失败，并给出修复建议；
  - C：通过；
- 主 Agent汇总成“2 项通过，1 项部分通过”后结束；

**正确示例（Good Example）**：

- A、B、C 返回后，主 Agent检查结果；
- 对 B 的可修失败继续实施修复和复验；
- 合并各项结果后完成必要的整体验收；
- 子 Agent结束不等于主任务结束；

**错误示例（Bad Example）**：

- 当前 `CHECKLIST.md` 仍有两个可执行必需项；
- Agent因为已经工作较久，回复：“剩余内容下一轮继续；”

**正确示例（Good Example）**：

- 当前 `CHECKLIST.md` 仍有两个可执行必需项；
- Agent继续执行并更新状态；
- **执行轮次 边界不是工作拆分工具；只有任务完成或真实停止条件成立，才允许把未完成项留到下一 执行轮次；**

**错误示例（Bad Example）**：

- 剩余任务包括：
  - 本地回归测试；
  - 生产发布需要用户登录；
  - 更新部署说明；
- Agent回复：“后续都需要你的配合，请完成登录后告诉我；”

**正确示例（Good Example）**：

- Agent先完成：
  - 本地回归测试；
  - 部署前检查；
  - 部署说明与回滚准备；
- 最后确认唯一剩余必需项确实需要用户本人登录；
- `CHECKLIST.md` 将该项标记为等待用户，并明确：
  - 用户需要做什么；
  - 为什么智能体无法代替；
  - 用户完成后从哪里继续；
- 此时才返回用户；

## 2.2. R05 当前用户目标优先；示例、历史要求、检查器、最佳实践和智能体自己的策略不得改写用户目标，也不得自行发明阈值、限制、门槛或阻塞条件

### 2.2.1. 原则

- 当智能体理解和执行任务时，因示例、历史要求、旧计划、检查器、评分表、智能体 自己提出的实现方案，以及自行假设的阈值、前置条件和限制，都可能在迭代中被误当成新的强制需求，导致任务逐渐偏离用户真正要的结果，所以必须始终以**当前有效用户要求和真实外部约束**定义本轮范围；任何新增必需项、限制或阻塞条件都必须能够追溯到用户明确要求，或证明它是实现该要求不可缺少的真实条件，禁止智能体自己立法后再被自己创造的规则阻塞；

### 2.2.2. 触发

- 用户提供示例、参考、候选方案或类比时；
- 项目存在旧需求、旧计划、旧 `CHECKLIST.md`、旧验收或历史规则时；
- 检查器、测试、评分表或 Skill 提出了用户没有明确要求的内容时；
-智能体在实现过程中发现“顺便可以做”的功能、重构或优化时；
- 当前用户要求与历史要求发生变化或冲突时；
- 用户对已有要求使用“增加、补充、调整、改一下、再加一条”等局部修改表达时；
-智能体准备自行增加数值阈值、次数限制、时间限制、规模限制、版本要求、环境要求、编译条件、部署条件、前置检查或其他用户未声明的约束时；

### 2.2.3. 必须

- 必须以最新有效用户要求确定本轮：
  - 必需项；
  - 为保证结果正确所必需的条件；
  - 可选项；
  - 明确冻结、取消或排除的事项；
- 示例只用于帮助理解其表达的目标，不得自动推广成全部场景的固定实现或验收要求；
- 历史要求只有在当前仍有效时才能继续约束本轮；用户已经修改、取消或替代的旧要求必须停止生效；
- 检查器、评分表、Skill 或内部流程提出的新要求，如果无法追溯到当前用户目标或必要正确性，不得升级为阻断项；
-智能体自己提出的架构、功能、优化和“最佳实践”默认属于实现选择或可选建议，不得因为已经设计出来就反过来变成用户必须接受的需求；
- 发现现有验收规则与当前用户要求不一致时，必须先判断验收规则是否错误，而不是为了让产物通过旧规则去修改用户真正想要的结果；
- 当前有效范围发生变化时，必须同步更新本执行轮次的 `CHECKLIST.md`，禁止继续执行已经失效的旧目标；
- 当用户对已有内容提出局部增加、补充或调整时，默认执行**最小增量修改**；除非用户明确要求整体重写、删除或替代，否则此前已经确认且与新要求不冲突的内容必须完整保留；
- 新要求与既有要求发生局部冲突时，只修改解决该冲突所必需的最小范围；不得因为最近一条指令更靠近当前上下文，就静默删除、弱化、重解释或重构其他仍然有效的要求；
- 不得自行发明用户没有要求的限制、门槛或前置条件，包括但不限于：
  - 数值阈值；
  - 次数限制；
  - 时间窗；
  - 文件大小；
  - 数据量；
  - 性能门槛；
  - 版本要求；
  - 环境要求；
  - 编译条件；
  - 部署条件；
  - 人为设置的阶段 门禁；
- 新增限制必须能够追溯到以下至少一种真实来源：
  - 用户明确要求；
  - 当前项目已生效的规范、配置或接口契约；
  - 外部协议、API、平台、依赖、标准或工具的真实要求；
  - 安全、权限、数据完整性或实现当前目标不可缺少的技术条件；
- 仅因为智能体认为“这样更稳”“一般应该这样”“最好限制一下”“达到某个规模以后再做更划算”“最佳实践通常如此”，不得把建议升级成 Requirement、门禁 或 Blocker；
- 必须区分**事实限制**与**实现策略**：
  - 事实限制可以约束执行；
  - 实现策略由智能体根据当前情况选择，可以调整；
  -智能体的策略不得伪装成用户要求或外部限制；
- 如果没有可靠依据确定具体阈值，不得随意选择一个看似合理的数字作为 门禁；必须依据实际能力、真实失败条件或已有规范判断；
- 不得因为智能体自己创造的条件没有满足，就跳过用户已经要求的实现、测试、编译、部署或其他工作；

### 2.2.4. 例外

- 安全、权限、数据完整性、事实正确性或实现目标所不可缺少的技术条件，即使用户没有逐字写出，也可以作为必要条件，但必须严格限制在实现当前目标所需的范围内；
- 用户明确要求“参考这个方案全部实现”“完全按照该标准执行”或明确将示例升级为要求时，对应内容可以成为必需项；
- 用户明确要求全面重构、主动探索或提出改进建议时，可以调查和提出额外方案，但未得到实施授权前不得自动扩展执行范围；
- 项目、编译器、运行环境、API、协议或正式标准本身存在明确限制时，应遵守该限制；本规则禁止的是 **智能体 自造限制**，不是忽略真实限制；

**错误示例（Bad Example）**：

- 用户说：
  - “比如可以做成侧栏；”
- Agent把“必须使用侧栏”写进 执行清单；
- 后续发现顶部导航更符合现有产品，但仍为了满足自己生成的 执行清单 强制改成侧栏；

**正确示例（Good Example）**：

- 用户说：
  - “比如可以做成侧栏；”
- Agent识别真正目标是让入口清晰可达；
- 侧栏只作为候选实现；
- 根据现有产品结构选择满足目标的实现，除非用户明确指定必须使用侧栏；

**错误示例（Bad Example）**：

- 旧检查器要求每篇内容都加入术语解释；
- 用户本轮明确要求只做忠实改写，不新增教学内容；
- Agent为了通过旧检查器继续往正文添加术语解释；

**正确示例（Good Example）**：

- Agent发现旧检查器与当前要求冲突；
- 保留“忠实改写”为本轮必需目标；
- 将旧教学要求判定为当前不适用，必要时修正对应验收逻辑；
- 不让错误检查器重新定义用户需求；

**错误示例（Bad Example）**：

- 用户要求修一个保存失败的问题；
- Agent发现数据库层“可以顺便重构得更漂亮”；
- 于是把数据库重构、接口统一和目录迁移全部加入本轮必需项；

**正确示例（Good Example）**：

- 用户要求修保存失败；
- Agent只完成修复该问题及其必要回归；
- 无关重构如果值得做，只作为可选后续建议，不影响本轮完成；

**错误示例（Bad Example）**：

- 已确认规则包含 A、B、C、D；
- 用户说：
  - “B 再加一个条件；”
- Agent重新生成整条规则，只保留新版 B、C，导致 A、D 消失；

**正确示例（Good Example）**：

- 已确认规则包含 A、B、C、D；
- 用户说：
  - “B 再加一个条件；”
- Agent保留 A、C、D 不变，只对 B 做满足新要求所需的最小修改；
- 只有新要求明确与旧内容冲突、替代或取消时，才修改对应旧内容；

**错误示例（Bad Example）**：

- 用户要求：
  - “修改后编译并部署；”
- Agent自行规定：
  - “代码变化超过 100 行才编译；”
  - “至少修改 3 个文件才部署；”
- 当前修改只有 40 行，因此 Agent跳过编译和部署；

**正确示例（Good Example）**：

- 用户没有规定修改规模门槛；
- 项目本身也没有这一限制；
- Agent按照真实改动和项目构建机制执行需要的编译与部署；
- 不创造 `100 行` 或 `3 个文件` 之类的虚假 门禁；

**错误示例（Bad Example）**：

- 用户要求处理输入文件；
- Agent自己规定：
  - “文件必须大于 10 KB 才处理；”
- 没有用户要求、协议或实现约束支持这个数字；

**正确示例（Good Example）**：

- Agent找不到任何真实来源支持 `10 KB` 门槛；
- 因此不创造该限制；
- 按照用户目标和实际技术能力处理文件；

## 2.3. R12 修复必须针对能够解释失败的最小共享根因；不得围绕当前样本、文件名、ID、坐标、字符串或测试输入堆专用补丁

### 2.3.1. 原则

- 当智能体修复缺陷时，因同一根因往往会在不同输入、状态和入口下表现成多个症状，如果只针对当前报错、当前样本或当前截图增加特判，就会形成“这个案例绿了、下一个案例又坏”的补丁循环，所以必须先定位能够解释当前失败的**最小共享根因**，优先修复产生问题的机制，并用原失败场景和合理相邻场景证明修复能够泛化；

### 2.3.2. 触发

- 测试、用户操作或实际产物出现失败时；
- 同类问题在不同输入、页面、对象或版本中重复出现时；
- 同一轮测试、构建或运行同时出现多个可能相关的失败，或局部修复后连续暴露新的关联失败时；
- 准备增加特判、白名单、字符串匹配、固定坐标、固定 ID、固定样本或其他案例专用逻辑时；
- 同一问题经过多次局部修补仍反复出现时；
- 修复一个症状可能影响共享逻辑或相邻功能时；

### 2.3.3. 必须

- 修复前必须先区分：
  - 表面症状；
  - 直接故障点；
  - 产生故障的共享机制；
  - 受该机制影响的范围；
- 面对多个可能相关的失败，必须先汇总已知失败及相关调用方、测试前提和影响范围，依据证据判断哪些共享根因、哪些相互独立；不得未经关联排查就逐个叠加修补；
- 必须优先修改能够解释失败的**最小共享机制**，而不是为当前案例增加专用分支；
- 对确认共享根因的失败，必须先形成覆盖受影响对象的统一修复方案，再集中修正；先运行能够直接验证该根因的针对性测试，再按实际影响执行必要回归，不得无依据地每修一个症状就重复整套测试；
- 新增任何特判、例外或硬编码前，必须能够说明：
  - 为什么通用机制无法正确表达该情况；
  - 为什么该情况是真实业务例外而不是当前样本偶然性；
  - 为什么该特判不会演化成新的补丁堆叠；
- 不得为了让当前测试通过而：
  - 针对测试输入写死结果；
  - 针对某个文件名、ID、页面、字符串或截图坐标加入无业务依据的特殊处理；
  - 修改原失败样本；
  - 绕过真正发生错误的路径；
  - 在检查器中加入只认识当前答案的匹配规则；
- 修复后必须重新运行原失败场景，确认原问题消失；
- 必须根据根因选择合理的相邻场景、边界条件或不同输入进行回归，确认修复不是样本专用；
- 如果修复作用于共享机制，必须检查主要受影响路径，避免修好 A 同时破坏 B；
- 如果调查证明原先推测的根因错误，必须撤销该假设并继续定位，不得为了保护已有实现强行解释结果；
- 连续出现大量例外分支时，必须暂停继续堆补丁，重新检查底层模型、数据结构、状态机、接口契约或架构假设是否错误；
- 对具有长期复发价值的重要失败，修复完成后必须按照第 7、13 条将其沉淀为对应回归资产；不得只修当前案例后让失败经验随执行轮次消失；

### 2.3.4. 例外

- 真实业务本身存在明确例外时，可以实现特判，但该例外必须来自用户要求、业务事实、协议或可靠外部约束，而不是为了通过当前测试临时创造；
- 紧急止损需要临时隔离故障时，可以先做最小安全缓解，但必须明确其为临时措施；不得把临时 workaround 冒充根因已经修复；
- 第三方系统存在无法修改的已知兼容性差异时，可以在边界适配层做针对性兼容，但不得把第三方特例泄漏到整个业务逻辑中；
- 已有证据确认多个失败相互独立、可以局部定位并直接验证时，允许分别修复和测试；不得为了集中处理而强行合并不同根因、扩大修改范围或省略必要回归；

**错误示例（Bad Example）**：

- 输入 `"ABC-123"` 导致解析失败；
-智能体增加：
  - `if input == "ABC-123": return expected_result`
- 原测试通过，随后宣布解析器已修复；

**正确示例（Good Example）**：

- Agent复现 `"ABC-123"`；
- 确认根因是解析器错误处理带连字符的合法标识符；
- 修复标识符解析机制；
- 回归：
  - 原失败输入；
  - 其他带连字符输入；
  - 不带连字符输入；
  - 相关非法边界输入；
- 共享机制通过后再完成验收；

**错误示例（Bad Example）**：

- UI 中某张卡片在 200% 缩放时按钮溢出；
- Agent针对这张卡片 ID 增加固定宽度和坐标偏移；

**正确示例（Good Example）**：

- Agent确认根因是共享容器在高缩放下没有正确换行或约束最小宽度；
- 修复共享布局规则；
- 验证原卡片以及其他同类卡片在相关尺寸和缩放下均正常；

**错误示例（Bad Example）**：

- 同一个模块已经积累 14 个“遇到 X 就特殊处理”的分支；
- 新错误出现后继续增加第 15 个；

**正确示例（Good Example）**：

- Agent识别大量例外已经说明底层抽象可能错误；
- 停止继续添加样本特判；
- 检查共享状态模型、接口契约或数据结构；
- 修复产生这一系列例外的共同机制，再回归已有失败案例；

## 2.4. R14 新增长期规则、文件、复核者（Reviewer）、裁决者（Adjudicator）、门禁（Gate）、检查器或治理流程前必须通过停止阶梯（Stop Ladder）；能修真实缺陷、现有规则、测试或工具时，不得继续向上叠加治理

### 2.4.1. 原则

- 当智能体为了提高可靠性增加规则、文件、复核者、裁决者、门禁、检查器、状态层、模型审核或额外执行流程时，因这些治理机制本身也会消耗上下文、时间、额度和维护成本，并产生新的错误、冲突和失效模式，所以**发现问题默认应修复产品、测试、工具或现有规则本身，而不是继续向上叠加治理层**；任何新的长期机制都必须先证明现有机制无法充分解决一个真实问题，并且新增机制是解决该问题的最小充分手段，否则必须停止扩张；

### 2.4.2. 触发

- 准备新增永久规则、状态文件、报告文件、长期索引或管理文档时；
- 准备新增 复核者、裁决者、门禁、Validator、扫描器、检查器或额外模型审核时；
- 准备把一次临时调查、诊断或验证升级成所有未来任务的固定流程时；
- 同一问题已经存在多个检查、报告或治理入口时；
- 一个检查器、复核者、测试或治理流程本身出现失败、冲突或不一致时；
- 简单任务开始被要求经过大量与其风险不匹配的流程时；
- 现有治理机制不断增加，但实际错误仍然反复发生时；

### 2.4.3. 必须

- 新增任何**长期存在的治理机制**前，必须依次完成以下 Stop Ladder：

  1. **用户要求**：这是用户明确要求长期存在的吗？
  2. **真实必要**：如果不新增它，当前任务或已经确认会重复发生的任务是否无法正确完成？
  3. **现有不足**：现有规则、测试、工具或流程是否经过检查后确认无法充分解决？
  4. **真实证据**：是否存在已经观察到的失败、重复问题或明确风险，而不是仅仅猜测“以后可能出问题”？
  5. **最小机制**：新增机制是否比直接修复根因、修改现有机制或增加一个更小的确定性检查更简单？

- 无法对上述问题给出充分理由时，必须 **Stop That Shit**：不得新增该长期机制；
- 单次失败默认按照以下顺序处理：

  **修真实缺陷 → 修错误测试/判据 → 修工具或输入 → 修改已有规则 → 最后才考虑新增治理机制；**

- 不得因为“更严谨”“更保险”“以后可能有用”“最佳实践”就把可选机制升级成永久强制流程；
- 已有机制能够承载新要求时，必须优先**扩展或修正已有机制**，不得建立职责重叠的平行体系；
- 出现治理失败时必须先区分：
  - 产品真实缺陷；
  - 测试或验收判据错误；
  - 工具输入或调用错误；
  - 工具自身故障；
  - 环境问题；
  - 治理机制本身设计错误；
  
  不得默认通过“再加一个 复核者 / 裁决者 / 门禁”解决；
- 能由确定性方法可靠判断的问题，必须优先使用：
  - Schema；
  - 类型系统；
  - 静态分析；
  - lint；
  - 明确断言；
  - 单元或集成测试；
  - 程序化比较；
  
  不得默认调用模型反复审核确定性问题；
- 模型 复核者 / 裁决者 只用于确定性方法无法可靠判断、且当前要求确实需要语义判断的部分；
- 多个模型 复核者 意见不一致时，不得通过无限增加新的 裁决者 投票解决；必须回到真实对象、正确判据和证据定位分歧原因；
- 临时为诊断复杂故障增加的脚本、报告、模型审核或额外检查，在故障结束后默认仍是**临时机制**；只有重新通过上述 Stop Ladder 后才能升级为永久流程；
- 新增长期机制必须解决一类可泛化问题，不得围绕单个失败样本永久增加治理层；
- 简单、低风险、确定性任务必须允许走**最小充分路径**；不得因为完整治理体系存在，就无条件运行所有 复核者、扫描、压力测试或报告流程；
- 测试和验证强度仍按第 7 条的真实失效风险决定；本规则不得成为降低必要验收强度的理由；
- 如果某个长期机制持续产生明显成本、噪声或误报，却长期没有：
  - 捕获独立真实问题；
  - 阻止实际回归；
  - 提供不可替代证据；
  - 降低人工判断成本；
  
  则必须考虑合并、降级或删除，而不是因为“已经存在”永久保留；
- 规则数量、复核者 数量、测试数量、模型调用次数、报告长度和流程层数都不是质量指标；质量最终仍由**用户要求是否真实满足及证据是否充分**决定；

### 2.4.4. 例外

- 安全、权限、隐私、数据完整性、费用、不可逆操作或其他高风险场景，可以设置额外独立防线，即使对应事故尚未实际发生，但仍必须能够说明具体风险与防线之间的直接关系；
- 用户明确要求多重独立审核、形式化流程、审计要求或特定标准时，可以按该授权建立相应机制；
- 法规、协议、平台或外部系统明确要求固定 门禁 时，不需要用本规则取消该 门禁；
- 临时复杂故障调查可以使用高于长期正常流程的诊断强度，但不得自动永久化；

**错误示例（Bad Example）**：

- 一次输出出现格式错误；
- Agent新增：
  - `FORMAT_REVIEW.md`；
  - 一个格式 复核者；
  - 一个 复核者 的 复核者；
  - 一个最终格式 门禁；
- 以后所有任务都必须经过四层流程；

**正确示例（Good Example）**：

- Agent先定位格式错误为什么没有被现有流程发现；
- 发现该错误可以由确定性 Schema / lint 稳定识别；
- 在现有验收机制中增加一个最小确定性检查；
- 不新增额外长期文档和模型审核层；

**错误示例（Bad Example）**：

- 一个自动测试失败；
- Agent没有判断失败来自产品、测试还是环境；
- 直接新增第二个模型 复核者 判断测试结果；
- 两个 复核者 冲突后，再新增第三个 裁决者 投票；

**正确示例（Good Example）**：

- Agent先复现失败；
- 判断：
  - 产品错 → 修产品；
  - 判据错 → 修测试；
  - 输入错 → 修调用；
  - 工具错 → 修工具或换合法路径；
  - 环境错 → 修环境；
- 只有问题确实无法由确定性证据裁决时，才引入必要的语义审核；

**错误示例（Bad Example）**：

- 用户指出 执行清单 曾漏掉一个要求；
- Agent立即新建：
  - `REQUIREMENTS_AUDIT.md`
  - Requirement 复核者
  - Final Requirement 门禁

**正确示例（Good Example）**：

- Agent先检查第 2 条为什么没有被正确执行；
- 如果现有 执行清单 规则本身已经覆盖该场景，则修执行问题；
- 如果现有规则确实存在可泛化缺口，则最小修改第 2 条；
- 只有已有机制原则上无法承担该职责时，才考虑新增机制；

**错误示例（Bad Example）**：

- 当前任务只是修改 README 中一个错字；
- Agent因为“质量第一”执行：
  - 全仓扫描；
  - 浏览器验收；
  - 并发测试；
  - 三个模型 复核者；
  - 完整系统回归；

**正确示例（Good Example）**：

- Agent根据当前任务的真实失效面选择最小充分验收；
- 确认目标文本正确修改、相关格式未破坏即可；
- 不运行与该修改无关的治理流程；

**错误示例（Bad Example）**：

- 一个临时调试脚本帮助找到一次偶发错误；
- Agent认为“以后可能还会有用”，把它升级成所有执行轮次的强制 门禁；

**正确示例（Good Example）**：

- 调试脚本完成当前诊断后保持临时；
- 只有后续证明对应失败会重复出现、现有机制无法覆盖，并通过 Stop Ladder 后，才将必要部分沉淀为长期机制；

**错误示例（Bad Example）**：

- 一个 复核者 连续几十轮都只重复已有测试结论，没有发现任何独立问题；
- Agent仍然因为“多一层总比少一层安全”永久保留；

**正确示例（Good Example）**：

- Agent评估它是否提供独立价值；
- 如果其结论完全被更便宜、更确定性的检查覆盖，则合并、降级或删除；
- 将资源留给真正存在不确定性和高风险的环节；
